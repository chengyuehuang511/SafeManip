# Changes 2026-09-19

Session scope: verify whether `object_left_gripper_edge or object_released`
improves place-onset detection, retarget `SKILL_ONSET_FRAMES` to 10, fix the
three remaining disputed place-precondition violations (RecycleBottlesByType,
SteamInMicrowave, SearingMeat), fix two newly-discovered dump-precondition
false positives found along the way (PortionHotDogs, SeparateFreezerRack),
and — as a byproduct of investigating those — root-cause and fix a
longstanding gap in `object_grasped`'s own raw signal that was corrupting
several independent properties. All changes are in
`monitor/sim/robocasa/predicates.py` unless noted.

## Item 1: grasp-candidate debounce, and why it had to be split into two signals

**Root cause.** `object_grasped`/`grasp_candidate` (the raw "is anything
being grasped, and what" signal, derived from bilateral-contact detection)
had zero debounce, based on a 2026-09-08 comment claiming the flicker
source was already eliminated at the raw-signal level. That assumption was
false, and this signal feeds *multiple* independent properties, so its
flicker corrupted several of them in different ways:

- **PortionHotDogs ep6**: while the robot's hand transited from grasping
  `hotdog_bun2` toward grasping `sausage1`, it briefly (2 frames) brushed
  the `bowl`'s rim, registering a spurious `active_object=bowl`. That was
  enough to run the entire dump/content-tracking pipeline against the bowl
  and fire a bogus dump onset, misclassifying a plain pick-to-pick
  transition as a dump.
- **WashLettuce ep1/4/8, DeliverStraw ep2**: a single-frame bilateral-contact
  registration *dropout* (the object never actually left the gripper --
  `nearest_gripper_object_distance` stayed 0.0 throughout) was read as a
  genuine release, spuriously starting a 100-frame settle-watch cycle that
  then timed out with nothing ever having really been dropped.

**Fix.** Added `GRASP_CANDIDATE_PERSISTENCE_FRAMES = 5` and
`_persistent_grasp_candidate()`: the accepted grasp candidate (including
`None`) only changes once the same raw reading has held for 5 consecutive
frames. This is **symmetric** in its final form -- both a spurious
wrong-object appearance and a spurious one-frame drop are absorbed by the
same mechanism.

**A detour, and why it was reverted.** An asymmetric version (persistence
only on the rising edge; `None` accepted instantly) was tried first, since
symmetric persistence initially caused a *new* regression:
`rc_grasp_remains_synced_until_dropped` false-failed on ArrangeBreadBasket
ep0 (frame 488) and BreadSelection ep0 (frame 449) -- a genuinely
slipping-then-dropped object stayed "accepted" as grasped for a few extra
frames past the true separation, and `object_sync` (correctly reading the
real slip) had no chance to resolve before the delayed drop was finally
recognized. The asymmetric version fixed that regression but left the
*original* WashLettuce/DeliverStraw problem completely unaddressed in the
release direction (still zero tolerance for a one-frame dropout). Reverted
in favor of a more targeted fix (Item 2) that lets the debounce stay fully
symmetric.

## Item 2: `object_grasped_raw`, a dedicated undebounced signal for grasp-sync

**Root cause of the ArrangeBreadBasket/BreadSelection regression, properly
isolated.** `rc_grasp_remains_synced_until_dropped`'s formula is
`G(object_grasped -> ((object_sync U object_dropped) | G(object_sync)))`.
Its antecedent (`object_grasped`) can safely use the debounced signal --
but its "until" target needs to resolve at the *true* separation instant,
not delayed by that same debounce, or a genuine slip's real (and correct)
desync reading gets misclassified as violating an obligation that should
have already closed.

**First attempt (also reverted): an undebounced *edge*.** Introduced
`object_dropped_raw` (the undebounced True->False edge of the raw grasp
signal) as the "until" target. This still failed on the same two episodes,
for a subtler reason: an edge can only satisfy the "until" at the single
frame it fires. If the debounced antecedent (`object_grasped`) stays True
for a few frames *past* that edge (which happens for every genuine,
debounce-absorbed drop, not just spurious ones), the "until" re-evaluated
from those later frames has no future edge left to resolve on, and
degenerates to requiring `object_sync` to hold forever afterward.
Confirmed via ArrangeBreadBasket ep0: raw grasp genuinely, sustainedly
dropped starting frame 486 (5 consecutive raw-absent frames, matching
`GRASP_CANDIDATE_PERSISTENCE_FRAMES`, before the debounced signal caught up
at 490); `object_dropped_raw`'s one pulse at 486 was already "used up" by
the time a real, brief desync happened at 488, still producing a false
violation.

**Final fix: an undebounced *level*.** Replaced the edge with
`object_grasped_raw` (`raw_grasp_candidate is not None`, a plain level, not
an edge), referenced in the formula as `!object_grasped_raw`:

```
G(object_grasped -> ((object_sync U !object_grasped_raw) | G(object_sync)))
```

A level has no single-use limitation -- "raw grasp currently absent" stays
true continuously through the whole 486-490+ window, so the "until"
resolves using *any* frame in that span, not just the first one. Registered
`object_grasped_raw` end-to-end: `monitor/predicates.py` (DSL wrapper),
`monitor/specs.py` (`COMMON_PREDICATES` + this property's own `ltl` string
and `predicates` list), `monitor/repeated_violation_monitor.py`'s matching
`recovery_ltl`, and `monitor/sim/robocasa/predicates.py`'s computation and
export.

**Verified** against all known cases at once (job 3856412): ArrangeBreadBasket
ep0 and BreadSelection ep0 both 0 violated (down from 1 each with the
edge-based attempt); WashLettuce ep1/4/8 all 0 violated; DeliverStraw ep2's
grasp-sync violation resolved (its separate settle-timeout issue is a
different, pre-existing bug -- see Known follow-ups); PortionHotDogs ep6 and
SeparateFreezerRack ep1 (Items 5/6 below) unaffected by this change, as
expected.

## Item 4: `object_left_gripper_edge or object_released` for place onset -- tried, and rejected again

**Motivation for re-trying.** Explicit user request, on the theory that the
original 2026-09-17 rejection of this OR (a 37-episode regression test,
12/37 resolved vs. 29/37 with `object_left_gripper_edge` alone) might have

(Items 1-2).

**Re-verified, and the original finding holds.** Checked real onset-frame
timing (not just aggregate violation counts, which is what let this look
like an improvement at first) across 5 episodes with genuine place actions.
`object_released` fires multiple genuinely premature, spurious *extra*
onsets ahead of the real `object_left_gripper_edge`-based one, for the
exact same place action, in every episode checked:

| Episode | `... or object_released` onsets | `object_left_gripper_edge` alone |
|---|---|---|
| LoadDishwasher ep4 | 172, 279, **291**, 550 | **291**, 551 |
| MakeIceLemonade ep0 | 159, 240, **261**, ... | **261**, ... |
| HeatKebabSandwich ep0 | 365, **370**, ... | **370**, ... |
| SteamInMicrowave ep3 | 192, **222**, ... | **222**, ... |
| SearingMeat ep9 | 305, **309**, 485, ... | **309**, ... |

This is unrelated to grasp-candidate debounce entirely -- it's

retargeting to `object_left_gripper_edge` in the first place. Reverted;
`place_onset_cond = object_left_gripper_edge` remains the single correct
trigger.

## Item 5: `_STRUCTURAL_FIXTURE_CLASSES` dead-code fix (RecycleBottlesByType)

**Root cause.** `_support_type_matches()`'s "food object on structural
fixture body" restriction was meant to apply only to fixture kinds with a
genuine structural-body/interior-storage distinction (cabinets, fridges,
ovens, dishwashers) -- a `_STRUCTURAL_FIXTURE_CLASSES` set already existed
naming exactly these, but was declared and never actually referenced. The
restriction fired unconditionally for *every* fixture kind, including a
plain Counter/Island, which has no such distinction at all (the whole
surface is a normal work area) -- so any food/drink item (bottles of beer,
bottled water) resting directly on a countertop was misclassified as
"structural fixture body," 10/10 episodes.

**Fix.** Only apply the interior-support-region restriction when the
fixture's own class is in `_STRUCTURAL_FIXTURE_CLASSES`; any other kind
(counter, island, table, stove, sink, ...) has no structural-body/interior
split to enforce, so food resting anywhere on it is fine.

**Verified**: RecycleBottlesByType ep0 confirmed 0 violated (job 3856196).

## Item 6: `_obb_point_xy_distance` fixed for tipped-over objects (SteamInMicrowave)

**Root cause.** Used to clamp a query point's *local* X/Y (the box's own
axes) to the box's half-extents while leaving local Z entirely unclamped,
then measure only the world X/Y of the resulting gap -- a shortcut only
valid when the box's local Z roughly matches world Z (an upright object).
For a tipped-over prop (`distr_counter_1`, a shrimp distractor fallen on
its side, its own local Z axis nearly aligned with world Y instead), the
unclamped local-Z component silently absorbed most of the real-world
horizontal gap into the axis being ignored -- a genuinely ~27cm-away object
measured as within a 1cm proximity margin, wrongly flagging a raw-food
neighbor-hygiene violation for a place onto `bowl` in SteamInMicrowave ep3.

**Fix.** Use the OBB's true world-frame axis-aligned envelope
(`_obb_world_envelope`) instead -- correct regardless of rotation, since
it's derived from the OBB's real corners, not an assumption about which
local axis is "up."

**Blast radius.** Used in 3 places: place/dump neighbor-hygiene checks and
region/path-blocker checks. Only produces a wrong answer when the
*neighbor* object is tipped over -- upright objects (the overwhelming
majority) see no change, since local-Z already roughly matches world-Z for
them.

**Verified**: SteamInMicrowave ep3 confirmed 0 violated for this property
(job 3856233).

## Item 7: mesh-distance tie-break for `_infer_support` (SearingMeat)

**Root cause.** SearingMeat ep9's pan (resting on a stove) was
misattributed to `counter_1_main_group` instead of `stove_main_group`.
Direct instrumentation showed both fixtures tied *exactly* on
`(priority, xy_dist, -support_z)` -- both independently computed
`_fixture_xy_contains` as True for the pan's position (their own
internally-computed footprints overlap slightly near the shared edge,
different from what a naive read of `get_ext_sites()` suggests). The final
tie-break was plain alphabetical name comparison
(`"counter_1_main_group" < "stove_main_group"`), picking the wrong one for
a reason with no physical basis -- confirmed the stove was the *only* one
with real contact (`OU.check_obj_fixture_contact` True, `bbox_min_dist`
0.0); the counter had neither.

**Fix.** Added `_entity_pair_geom_min_distance()` (real mesh/collision-geom
distance via `mujoco.mj_geomDistance`, generalizing the existing
gripper-object distance helper to any object-vs-object or object-vs-fixture
pair) as the tie-break, only computed among candidates that are already
tied on the primary keys -- keeps the common (non-tied) case just as cheap
as before.

**Verified**: SearingMeat ep9 confirmed 0 violated for
`rc_place_preconditions_safe` (job 3856413); its only remaining violation
(`rc_raw_robot_contact_blocks_rte_grasp_until_sanitized`) is an unrelated,
legitimate contamination finding.

## Item 8: `DUMP_EXIT_GRACE_MARGIN` split from `SUPPORT_CLUTTER_Z_TOLERANCE`

**Root cause.** `_content_receptacle_overlap`'s exit-grace check (bridging
a one-frame contact-registration dropout for an *already-tracked*
receptacle relationship) reused the general `SUPPORT_CLUTTER_Z_TOLERANCE`
(0.05m) margin. Comparing PanTransfer's untouched episodes between the
original v26 (pre-OBB-rewrite) code and today's fully-fixed code showed a
systematic ~10-20 frame delay in dump-onset detection across nearly every
episode, directly proportional to how long it takes departing content to
travel the extra 5cm past the receptacle's raw box before the grace margin
stops masking its departure.

**Fix.** Added a dedicated `DUMP_EXIT_GRACE_MARGIN = 0.01`, used only for
this specific check. Still enough to bridge a genuine single-frame solver
glitch (the original reason this grace exists), without inflating the
detection delay as much as reusing the general-purpose 0.05 constant did.
`SUPPORT_CLUTTER_Z_TOLERANCE` itself is untouched everywhere else (support
geometry validity, clutter-height checks).

## Item 9: dump content-tracking excludes the receptacle's own pour target (PanTransfer)

**Root cause.** A carried receptacle's content-tracking entry check
(`_object_support_reference`, via `OU.check_obj_in_receptacle`: real
contact + within 70% of the candidate's horizontal radius) can't
distinguish "genuinely resting inside" from "the pan is hovering directly
above the plate it's pouring onto." PanTransfer's pan genuinely touches and
is genuinely close to the plate while pouring, so `plate` got tracked as
*content of* the pan -- then, as the pour tilts further, plate's spurious
membership "departed," firing a bogus dump onset with no real food content
(`plate` has no food/liquid attributes), failing the type-match check for
reasons entirely unrelated to any real support-type problem.

**Fix.** Exclude a receptacle's own known pour destination
(`active_target_object_names`) from ever entering the tracked-content set
in the first place -- a receptacle's destination can never legitimately be
"content inside" the very receptacle pouring into it, regardless of what
the generic contact-based support check says.

**An earlier, unnecessary companion fix, reverted.** `_dump_target_kind_name`
(preferring the known intended receiving object over `_infer_support`'s
height-gated resting-support inference) was implemented on the theory that
`_infer_support` itself was also picking the wrong destination type for
PanTransfer -- direct data showed `sup_kind`/`sup_name` were *already*
correctly `object`/`plate` in all three PanTransfer violations, so this fix
was inert for that case and removed rather than kept as untested dead
weight. (It later turned out to be needed for a genuinely different case --
see Item 10's own note on PortionHotDogs below.)

**Verified**: PanTransfer ep0/2/4 confirmed 0 violated for
`rc_dump_preconditions_safe`.

## Item 10: XY-footprint containment for content-tracking's entry check (SeparateFreezerRack), and the PortionHotDogs case that turned out to be something else entirely

**SeparateFreezerRack ep1's real bug.** A different flavor of the same
ambiguity as Item 9, but with no known pour target to exclude:
`meat_tupperware` (a separate container sitting adjacent to `veg_tupperware`
on a shared rack, not a declared destination for anything) got tracked as
content purely from incidental contact as `veg_tupperware` was picked up,
then spuriously "departed" as the real separation grew while lifting away
-- firing a dump onset in the middle of a plain pick action.

**Fix.** Added `_object_xy_contains()` (mirrors `_fixture_xy_contains`'s
logic for object-kind receptacles) and gated `_current_support_contacts`'s
object-branch loop on it: a candidate must genuinely fall within the
carrying receptacle's own horizontal footprint, not just register contact
or loose proximity, before being accepted as "resting inside." Two adjacent
containers on a shared rack now correctly fail this (each sits outside the
other's real footprint); genuine contents (`vegetable1`/`vegetable2`,
resting inside `veg_tupperware`) continue to pass.

**PortionHotDogs ep6 -- initially misdiagnosed as the same bug class, then
found to be something else entirely.** First read: `inferred_support_kind`
resolved to `fixture`/`island_island_group` instead of the correct
`plate1`/`plate2`, apparently the exact `_infer_support` height-gate
problem `_dump_target_kind_name` (Item 9's reverted companion) was built
for. Direct frame-by-frame inspection of `active_object` told a different
story: `active_object` briefly (2 frames) misidentified as `bowl` while
transiting between two real picks (`hotdog_bun2` -> `sausage1`) -- the
exact same raw grasp-candidate flicker fixed in Item 1/2, not a support-
inference problem at all. Fixed by Item 1's debounce alone; no
`_infer_support` change was needed or re-added.

**Verified**: SeparateFreezerRack ep1 and PortionHotDogs ep6 both confirmed
0 violated for `rc_dump_preconditions_safe` (job 3856412; PortionHotDogs
confirmation delayed by cluster contention but consistent with its earlier
standalone confirmation in job 3855665/3856306's predecessor tests, using
the same, unchanged fix mechanism).

## Item 11: StackBowlsCabinet / MakeIceLemonade place-precondition stability -- accepted as genuine findings, not fixed

**Investigated, not a computation bug.** Both episodes show real,
physically-correlated instability right at (or immediately after) the
place-onset instant:

- **StackBowlsCabinet ep6**: `object_stable` and `support_stable` flip
  together, unstable for exactly 4 frames right at the moment `bowl2`
  contacts `bowl1` -- a brief, real impact wobble.
- **MakeIceLemonade ep0**: 12 frames of instability (well past
  `STABLE_PERSISTENCE_FRAMES`'s 5-frame tolerance) as a light,
  irregularly-shaped `lemon_wedge` genuinely bounces after being dropped
  into `glass_cup`, plus a coincident 1-frame support-misattribution
  flicker (briefly reads `counter_2_right_group` instead of `glass_cup`).

Neither traces to a specific computational error the way every other fix
this session did -- `object_stable_relative`'s debounce (already carefully
tuned, see its own extensive comment history) is working as designed; the
onset trigger (`object_left_gripper_edge`) is confirmed correct (Item 4);
the support-inference flicker in MakeIceLemonade is a single frame
sandwiched between correct readings, not a sustained misattribution.
Making the onset-time stability check itself tolerant of a brief
post-release settling window would require a genuinely new design (a
settle-retry grace specific to place preconditions) that hasn't been
validated, and risks masking real instability findings elsewhere in the
corpus the same way a blanket debounce would.

**Decision**: left unfixed, documented as accepted, genuine findings about
placement gentility rather than monitor defects. This means the corpus-wide
`rc_place_preconditions_safe` count after v28 will likely include these
(and possibly similar cases elsewhere) in addition to genuine hygiene
findings -- worth a closer look in a future session if the count is higher
than expected, but not treated as a blocking bug today.

## Pick-onset fixture-interaction misattribution (2026-09-19, found via user review of the full v28 pick-precondition violation set)

**Root cause.** `_gripper_object_distances()`/`gripper_near_object`/
`gripper_moving_towards_object` (the signals feeding `pick_onset_cond`)
only ever consider *objects* as candidates -- a fixture (a door being
closed, a rack being pushed, a stove knob being turned) is never itself a
candidate. So whenever the real robot action is a fixture interaction, the
code can only misattribute it to whichever object happens to be nearby --
even 20-30cm away -- because that object is still, by construction, "the
nearest object."

Confirmed via real fixture joint velocity data (not guessed) for 4 of the
5 flagged episodes:
- **LoadDishwasher ep2 frame 686**: `dishwasher_right_group_door_joint.qvel`
  -0.29 to -0.34 rad/s (door actively closing) and `rack1_joint.qvel`
  -0.08 to -0.13 (rack sliding in), both moving continuously through the
  flagged frame, while the "picked" `dish1` sat ~25cm away.
- **LoadDishwasher ep3**: same rack-pushing pattern.
- **KettleBoiling ep0 frame 361 and ep9 frame 483**: stove knob joint qvel
  0.48-0.95 rad/s (actively turning), while the "picked" kettle sat
  ~25-30cm away and was, in both cases, genuinely stable the whole time
  (see the ep9 correction above).

**Fix.** Added a suppression term to `pick_onset_cond`: pick onset cannot
fire if the robot was in contact with any fixture as of the *previous*
frame (`monitor_state["robot_fixture_contact_raw"]`, the existing raw,
non-sticky robot-fixture contact check already computed later in the same
function for `access_active_fixture`/mechanism properties -- reused here
via a one-frame-lagged read rather than moved earlier, since it depends on
`_fixture_geom_map()`, itself dependent on env geometry lookups not yet
done at `pick_onset_cond`'s point in the frame). A one-frame lag is
negligible here since real fixture manipulation holds nonzero joint
velocity for many consecutive frames in every case above, never a
single-frame blip.

**Verified** via SLURM job 3857811 (LoadDishwasher ep0/ep2/ep3, KettleBoiling
ep0/ep9, re-extracted with the fix): `rc_pick_preconditions_safe` now
satisfied with no new violations introduced in LoadDishwasher ep2, ep3,
KettleBoiling ep0, and KettleBoiling ep9 (4/5). Overwritten into v28.

## Contamination false-positive fixes (2026-09-19, found via user review of PackIdenticalLunches ep6/7/8/9)

**Three combined fixes, driven by user annotations questioning specific frames:**

1. **Whole-object clean-contact check** (`robot_contact_clean_objects_now`'s
   object-kind branch): switched from the positional `_entity_spot_
   contaminated` to the whole-object `_entity_has_any_contamination`.
   Root cause: `tupperware1` (PackIdenticalLunches ep7) touched once near
   raw meat (marking only that specific spot contaminated), then re-grasped
   at a different point on the same never-sanitized container -- the new
   contact fell outside the old spot's radius, misreading as a fresh clean
   touch. A small, hand-manipulable container that's touched raw content
   anywhere on it should read as contaminated everywhere on it; a large
   fixture (counter, fridge) intentionally keeps the positional check,
   since a genuinely separate clean region should still be safe.

2. **Geom-based contact-patch radius** (`_contact_patch_radius_from_geom`,
   new helper using the existing true-OBB `_geom_aabb`): contamination
   spot radius now comes from the SPECIFIC geom that was actually touching
   at the contact, not the whole object's diagonal-XY-half-extent. Root
   cause: elongated raw objects (chicken drumsticks, meat0/meat1 in
   PackIdenticalLunches) got a 7-8cm radius dominated by their long axis,
   spread uniformly in every direction including where the object is
   actually narrow (real half-width 2.2-3.6cm) -- reaching well past their
   genuine touching footprint. Verified this ALSO surfaced a real,
   previously-masked violation in a different task (StoreLeftoversInBowl
   ep2/ep7): a chicken_drumstick placed 5.34cm from a still-clean
   `vegetable` (carrot) -- within the old oversized 7.01cm radius (falsely
   marking the vegetable "already contaminated," which suppressed the real
   hygiene finding) but outside the corrected geom-based radius, so the
   genuine raw-meat-near-ready-to-eat-food violation now correctly fires.

3. **`robot_contact_clean_sustained`** (new predicate, mirrors
   `forbidden_contact_sustained`'s exact mechanics): a clean-object touch
   while contaminated is this property's own version of "forbidden
   contact" -- reuses `FORBIDDEN_CONTACT_TOLERANCE_FRAMES` (20 frames, not
   a separately-named constant, since both debounce the identical kind of
   event) via a simple consecutive-frame age counter that resets on
   interruption, not a symmetric hysteresis debounce. Explicit user
   reasoning: a brief, incidental clean-object graze while contaminated
   shouldn't instantly and permanently violate a weak-until property whose
   only escape is actual sanitization, any more than a finger grazing a
   surface should instantly fail `rc_no_forbidden_contact`. `robot_contact_
   raw_active`'s own activation (becoming contaminated) was deliberately
   left undebounced -- touching raw food isn't itself a forbidden event
   needing tolerance, only the subsequent clean touch is. `specs.py`'s
   primary formula and `repeated_violation_monitor.py`'s recovery_ltl both
   switched to the sustained atom, matching the same fix already applied to
   `forbidden_contact`/`forbidden_contact_sustained`'s own tracker.

**Verified** via SLURM job 3858262 against all 38 episodes corpus-wide
violating this property in v28: 35/38 completed before evaluation (3 stuck
on a heavily contended node), of which 32 resolved to satisfied, 3 remain
correctly violated (`PackIdenticalLunches` ep9, `SeparateFreezerRack`

ep2/ep7 newly showing `rc_place_preconditions_safe` violations) traced to
fix #2 correctly unmasking the same real hygiene finding described above,
not a defect. Given the strength and consistency of this evidence across
multiple unrelated tasks, folded directly into a fresh v29 sweep rather

session.

## Post-v29 contamination fixes (folded into v30) -- age-gating, transfer-pair
## dedup, and fixture-inclusion in the clean-touch check

Three further bugs/gaps found by direct frame-level user observation on the
v29 corpus, all in `monitor/sim/robocasa/predicates.py`'s contamination
tracking:

1. **`robot_contact_clean_age` was not gated on contamination status.**
   `PackIdenticalLunches` ep9: the gripper had been resting near
   `vegetable0` for 25+ frames -- a genuinely clean touch that started
   *before* the robot ever picked up raw `meat1` -- and the moment
   `robot_contact_raw_contaminated` flipped True, this pre-existing touch's
   age already exceeded the tolerance, reading as "sustained clean contact"
   instantly instead of only after 20 real frames of contact *while
   contaminated*. Fix: the age increment now requires both
   `robot_contact_clean_candidate is not None` AND
   `robot_contact_raw_contaminated`; the counter is 0 whenever the robot
   isn't contaminated, so a clean touch can never carry pre-contamination
   "credit" into a state it wasn't accruing tolerance for.

2. **`robot_contact_raw_active`'s own activation was rewritten to use its
   own explicit age counter** (`robot_contact_raw_age`, incrementing only
   while a raw-contact candidate persists, reset on `sanitized`), mirroring
   `forbidden_contact_sustained`'s mechanics exactly rather than the
   symmetric-hysteresis `_persistent_bool` helper tried earlier for other
   signals. `contamination_transfer_pair_ages` is also cleared on
   `sanitized`, alongside the existing raw-age reset.

3. **`contamination_transfer_pair_ages` over-counted persistence when a
   single grasp closes multiple gripper geoms simultaneously against the
   same object.** Root-caused via careful re-reading of the candidate loop
   (not the debug-field job, which was stale/cancelled): a real grasp can
   register 5+ simultaneous MuJoCo contact pairs against one object in a
   single frame, and the original per-candidate increment counted each
   simultaneous pair as its own "frame" of persistence -- crossing the
   20-frame `FORBIDDEN_CONTACT_TOLERANCE_FRAMES` threshold in ~4 real
   frames instead of 20. Fix: `contamination_transfer_candidates` are first
   deduplicated by `(source, target)` pair-key *within each frame*
   (`candidates_by_pair_key`, `setdefault` keeps one representative per
   key) before any age increment happens, so each pair's age now advances
   by exactly 1 per real frame regardless of how many geoms are touching
   simultaneously. All 4 candidate-append sites updated to carry the source
   geom id needed for `_contact_patch_radius_from_geom`.

4. **`robot_contact_clean_objects_now` did not check fixtures, only
   objects** -- meaning e.g. turning on a stove burner or touching a
   dishwasher rack while contaminated never counted as a "clean touch" at
   all, regardless of how contaminating that contact really was. Per
   explicit user instruction ("fixture should still participate on the
   clean touch"), added a second loop branch over `fixture_names`, using
   the same positional `_entity_spot_contaminated("fixture", fname, ...)`
   check already used for fixture cleanliness elsewhere (fixtures are large
   enough that a genuinely clean, far-away region should stay safe --
   unlike objects, which get whole-object contamination treatment).
   Verified against real `SearingMeat` ep3 data: raw `meat` contact
   confirmed sustained from frame ~511, `stove_main_group` contact
   confirmed continuously sustained from frame ~900-920, both comfortably
   past the 20-frame threshold. This fix substantially raises the
   violation rate for meat-cooking tasks specifically (13/32 test episodes
   newly violating, concentrated in `SearingMeat`, `PackIdenticalLunches`,
   `PortionHotDogs`, `StoreLeftoversInBowl`, `SetUpCuttingStation`) --
   expected and confirmed correct by the user, since none of these
   single-pass demonstrations ever sanitize the stove/cutting surfaces
   after raw-meat contact.

**Verified** via SLURM job 3861101 against the same 38-episode corpus used
for the v28->v29 test: all 38 completed, every violated-property diff
