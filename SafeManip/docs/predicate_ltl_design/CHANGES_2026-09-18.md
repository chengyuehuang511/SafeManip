Session scope: fix disputed v26 annotations across three categories (place

## 1. True oriented-bounding-box (OBB) geometry rewrite (global)

**Root cause.** Every geometry helper in this file (`_object_aabb`,
`_fixture_aabb`, `_aabb_intersects`, `_aabb_distance`, `_other_name_is_below`,
etc.) worked in terms of world-frame *axis-aligned* bounding boxes. For a
rotating object (a container being tilted to pour), the true box doesn't
change size, but its world-frame axis-aligned envelope inflates as it
rotates -- confirmed via PanTransfer ep9: `vegetable_container`'s AABB
"top" kept climbing purely from tilt, with nothing physically separating,
which broke `_other_name_is_below`'s "is the support's top below my
bottom" world-Z ordering check well before the container's contents had
actually left it.

**Fix.** Replaced the AABB system with a genuine oriented-bounding-box
(OBB) representation: `(center, axes, half_extents)`, where `axes`'
columns are the box's own local unit axes in world coordinates (same
convention as MuJoCo's `geom_xmat`/`body_xmat`). Every box constructor
(`_object_aabb`, `_fixture_aabb`, `_fixture_interior_support_aabb`,
`_geom_ids_obb`, etc.) now builds a true OBB from the relevant body's live
rotation instead of a world-axis-aligned envelope. Core primitives
(`_obb_sat_intersects` -- a standard 15-axis separating-axis test,
`_obb_distance`, `_obb_closest_point_on_top_face`, etc.) live near the top
of the module. Existing function names (`_aabb_intersects`,
`_aabb_distance`, ...) are kept as thin wrappers so the ~45 existing call
sites didn't need to change, only the handful of places that did raw
`aabb[0]`/`aabb[1]` min/max indexing (now `.` into the OBB's own
center/axes/half fields, or `_obb_world_envelope(obb)` where a genuine
world-frame envelope is still the right concept, e.g. clutter-height
checks).

**`_other_name_is_below` removed entirely** (was: "is `other_name`
positioned at/below `name`'s own bottom, within a 5cm tolerance").
Rotation makes any world-Z ordering test unreliable (not just the
axis-aligned envelope but even the two objects' own *center points* can
swap relative height mid-tilt). It was originally added to stop a
freshly-placed object from being treated as its own receptacle's support
(ArrangeTea ep0), but that's now independently prevented by
`_is_plausible_support_object`'s receptacle-category restriction (added
earlier the same day) -- a non-receptacle candidate is filtered out before
this check would ever run. Genuine (non-inflated) OBB intersection is a
strictly more reliable "are they touching" signal, rotating or not.

## 2. Dump/content-tracking: swept-past false positives

**Root cause (two layers).**
1. A carried receptacle's content-tracking used `_object_support_reference`,
   which is rigorous (real contact + category-restricted) but MuJoCo's own
   contact-registration bookkeeping can drop for a single physics step
   during dynamic motion (confirmed: PanTransfer ep9 frame 102, contact
   read False for exactly one frame while genuinely still touching on
   every neighboring frame).
2. A naive fix (accept raw OBB-overlap as a fallback, in the *general*
   `_current_support_contacts` function used by many callers) reintroduced
   the original class of bug from a different angle: a moving/rotating
   candidate's *coarse box corner* can geometrically graze an unrelated,
   merely-nearby stationary object, with no real touching at all
   (reproduced for both `LoadDishwasher` ep4's dish0/dish1 and
   `PanTransfer` ep9's vegetable_container/plate).

**Fix.** The OBB-overlap grace fallback was removed from
`_current_support_contacts` (too broad a scope -- it's used for general
support inference, pick/place blockers, clutter checks, not just dump
tracking). Instead, `_content_receptacle_overlap` (the dump/content
tracking function) gained an `allow_geometry_grace` flag, set `True` only
for the "is an *already-tracked* content item still there" exit check --
never for "should this newly become tracked" entry check. This means a
coarse-box coincidence can excuse a single dropped contact-registration
frame for a relationship already established by real contact, but can
never fabricate a new one. The grace check itself uses
`SUPPORT_CLUTTER_Z_TOLERANCE`-expanded boxes (not shrunk -- see the
function's own docstring for the reasoning: since fabrication risk is
already closed off by the entry/exit scoping, the remaining tradeoff is
"too strict risks a false exit (hard misclassification)" vs. "too lenient
only delays detecting a real exit by a few frames (soft cost)", and the
soft cost is preferable).

**Verified against all 6 originally-disputed dump-onset annotations**
(LoadDishwasher ep4, PanTransfer ep0/2/4, ScrubCuttingBoard ep2/3): the
disputed frame no longer fires an onset in any of them. Several later
surfaced a *genuine* dump-type-mismatch finding further downstream in the
same episode (once the false positive stopped truncating the trace early)
-- these are new, real findings, not regressions.

## 3. Support-geometry validity: real gap tolerance restored

Replacing `_other_name_is_below`/world-Z ordering with plain OBB
intersection in `_support_geometry_valid`/`_dump_support_geometry_valid`
(object-kind branches) lost the old check's deliberate small-gap
tolerance (bounding-box coarseness, MuJoCo's own contact margin, genuine
physical clearance between two resting surfaces). Restored via
`_expanded_aabb` (a new small helper: grow an OBB's half-extents along its
own local axes by a margin, clamped to non-negative) applied with
`SUPPORT_CLUTTER_Z_TOLERANCE` before testing intersection in these two
specific validity checks. (The separate OBB-overlap fallback inside
`_current_support_contacts`'s object-contact loop intentionally does *not*
get this same margin -- it's a backstop for a literal one-frame solver
glitch, where the true geometry is already known to overlap at zero
tolerance, not a primary validity gate.)

## 4. Fixture interior-geometry degenerate-site fallback

**Root cause.** `_fixture_interior_support_aabb` (drawer/cabinet/fridge
interior placement surfaces) reads RoboCasa's own live
`fixture.get_site_info(sim)` MJCF `<site>` elements. For at least two
fixture instances (`SetUpCuttingStation` ep2's `stack_1_right_group_2`
drawer, and `LoadDishwasher`'s dishwasher rack), these separate `<site>`
elements are essentially coincident (a near-zero-volume box) even though
`get_site_info` genuinely, correctly queries them live -- an asset
inconsistency for these specific fixture variants, not a live-tracking
bug (not something SafeManip can fix in the asset itself).

**Fix.** When the site-derived interior box is degenerate (any half-extent
< 1cm), fall back to the region's own *geom*-based local corners
(`fixture._regions`, computed from the geom's real pos/size at
model-build time -- confirmed correctly sized) transformed by the live
pose of whichever body owns that region's `reg_<name>` geom (found via
`geom_bodyid`, not the fixture's static root pos/rotation -- the same
"live body pose, not nominal fixture pose" principle already established
for the site-based path).

**Verified**: `SetUpCuttingStation` ep2's disputed "why is the geometry
invalid" annotation is resolved (the only remaining violation in that
episode is unrelated).

## 5. Fixture-relative object stability

**Root cause.** `_object_stable_relative` (used by pick/place stability
checks) only corrected for an *object*-kind support's own velocity
(`_object_support_reference` -- "fixture supports are treated as
stationary" was its own long-standing, explicit assumption). True for a
static counter/shelf, but wrong for an articulated fixture whose relevant
part is genuinely moving: an item resting motionlessly inside a drawer
being pulled open reads as "not stable" purely from inheriting the
drawer's own world-frame motion, not any real rattling (confirmed via
`PickPlaceDrawerToCounter` ep3/7's disputed "spoon lying in the drawer the
whole time, why not stable" annotations).

**Fix.** Added `_fixture_support_reference` (the fixture-kind counterpart
to `_object_support_reference`) and `_fixture_velocity_near` (live
`(linear, angular)` world-frame velocity, via MuJoCo's `cvel`, of
whichever body of the fixture is physically closest to the object's
position -- an approximation for "the specific articulated part this
object is actually resting on," since a fixture's geoms can span several
independently-jointed bodies and the exact contact geom isn't tracked at
this call site). `_object_stable_relative` now falls back to this
fixture-relative correction whenever there's no object-kind support.

**Verified**: `PickPlaceDrawerToCounter` ep3 and ep7 both went from 1
violated (pick preconditions: object not stable) to 0 violated / 20
satisfied.

## 6. Contamination: spot-based, not whole-body

**Root cause.** `contaminated_objects`/`contaminated_fixtures` were flat
`set[str]`s of object/fixture *names*. The instant any single point on a
body was touched by something raw/contaminated, the *entire* body counted
as contaminated -- reasonable for a small object, but wrong for anything
with real spatial extent: a fridge's several shelves, a cabinet's several
compartments, or a bowl's far rim vs. near rim, none of which should be
implicated by contact with a physically distant, never-touched part of
the same body (confirmed via `PackIdenticalLunches` ep1's disputed
"vegetables and meat aren't on the same shelf, why does the whole fridge
become contaminated" annotation).

**Fix.** Replaced both sets with one unified `contaminated_spots: list[dict]`,
each record `{"kind": "object"|"fixture", "name", "body_id",
"local_offset", "radius"}`. Contamination now spreads only to the actual
contact point, with `radius` set to the *contaminating* entity's own
footprint size (a large pot contaminates a bigger area than a small lemon
slice; per explicit user decision). Critically, the spot's position is
stored as a **body-relative local offset**, not a raw world position, and
resolved back to world coordinates from the owning body's *current* live
pose every frame -- necessary because both objects (a bowl can be picked
up and moved) and articulated fixture parts (a drawer) can move after
being contaminated; a world-frame spot would silently become wrong the
instant the contaminated thing moved.

Two query modes:
- `_entity_spot_contaminated(kind, name, position)`: is the specific spot
  at `position` on this object/fixture contaminated -- used for support-role
  checks (is the spot a manipulated object is resting on contaminated).
- `_entity_has_any_contamination(kind, name)`: broad, non-positional --
  used for self-checks (is this object itself, as a whole, now considered
  contaminated, e.g. for ready-to-eat status), where there's no other
  specific spot to check against.

**Verified**: only 2 spots recorded across all 885 frames of
`StoreLeftoversInBowl` ep1 (no runaway growth from contact-position
jitter -- the "already covered" check in the transfer-candidate loop
correctly suppresses duplicate spots for a stationary resting contact).
`StoreLeftoversInBowl` ep1's disputed "why is the bowl contaminated"
annotation resolved as a side effect of the OBB support-inference fix
(item 1) -- the vegetable's support now correctly resolves to `bowl`
itself, not the counter fixture that was actually contaminated.

## Item 7: dishwasher rack XY-containment fix (LoadDishwasher ep4)

Root cause, found via direct debugging (`debug_loaddishwasher_rack.py`,
`_rack2.py`, `_scoring.py`): `_fixture_xy_contains(fname)` -- used by
`_infer_support`'s dishwasher-shortcut branch to decide whether an
object's XY position falls inside the dishwasher's footprint -- was
checking the fixture's **static exterior housing** footprint
(`_fixture_aabb` -> `_fixture_ext_sites_aabb`, computed at the fixture's
static root pose). A dishwasher's rack slides *forward*, out of the
housing, when the door is open, so an item resting in the extended rack
can genuinely sit outside the housing's static exterior footprint.
Confirmed directly: the housing's ext-sites bounds were
`[2.2, -0.6]` to `[2.85, 0.0]` while `dish0`'s actual position was
`[2.526, -0.733, 0.563]` -- Y=-0.733 falls outside the housing's
`[-0.6, 0.0]` range even though `dish0` is correctly resting on the
(extended) rack.

Fix: added a `use_support_aabb: bool` parameter to
`_fixture_xy_contains(fname, use_support_aabb=False)`. When `True`, it
uses `_fixture_support_aabb(fname, obj_pos=mpos)` (which for
dishwasher-text fixtures resolves to the rack's own *live* extent via
`_fixture_rack_aabb`, not the static housing) instead of the housing
footprint. The dishwasher-shortcut call site in `_infer_support` now
passes `use_support_aabb=True`. This was a genuinely different bug from
item 4's degenerate-site fallback -- `_fixture_interior_support_aabb`'s
region geometry was already valid here (confirmed: real, non-degenerate
`fixture._regions['rack0'/'rack1']` corners, ~46cm x 34cm x 26cm), the
bug was entirely in the XY-containment gate deciding whether to even
consider the dishwasher as a support candidate in the first place.

This first fix resolved the support-type-mismatch (frame 291 now
correctly resolves `dishwasher_main_group` instead of `floor_room`), but
re-extraction (job 3855008) surfaced a second, narrower instance of the
exact same bug class: `_support_geometry_valid`/
`_dump_support_geometry_valid`'s fixture-kind branch was still checking
`OU.point_in_fixture(..., only_2d=True)` / `fixture.get_ext_sites()` --
both resolve against the fixture's *static exterior housing* footprint,
not the rack's live extent -- so even after the support correctly
resolved to `dishwasher_main_group`, the geometry-validity check on that
same support still rejected it (`"support geometry was invalid"` at
frame 291). Fixed both occurrences (`_support_geometry_valid` for
place-preconditions, `_dump_support_geometry_valid` for dump
preconditions) to use `_fixture_support_aabb(sup_name, obj_pos=support_pos)`
plus a local-XY-half-extent containment check, mirroring
`_fixture_xy_contains`'s logic, instead of the static-footprint checks.

**Confirmed via re-extraction (job 3855521):** `LoadDishwasher` ep4 went
from 2 violated / 18 satisfied to 1 violated / 19 satisfied. Both
disputed annotations ("frame 525 is a place, not a dump" and "why the
support type matches object is false?") are resolved. The one remaining
violation (`rc_pick_preconditions_safe` at frame 153, `dish0` not stable
at pick onset) was never a disputed annotation -- it's a separate,
undisputed observation from earlier documentation, left as-is.

## Item 8: dump content-tracking spuriously includes the pour destination (PanTransfer ep0/2/4)

**Root cause.** The 3 "genuine new findings" reported earlier in item 2's
verification (PanTransfer ep0 frame 319, ep2 frame 498, ep4 frame 331 --
all `rc_dump_preconditions_safe`, "support type doesn't match content")
were themselves still false positives, not real findings (caught by user
review). Traced via `violation_evidence`'s `grasped_receptacle_content_
names`/`dump_content_names_for_preconditions` fields at those frames: in
all three episodes, `'plate'` -- the object the pan is pouring vegetables
*onto*, not something inside the pan -- was itself spuriously tracked as
*content of* the pan (`vegetable_container`). This happens because content
entry-tracking relies on `_object_support_reference`, which in turn calls
RoboCasa's own `OU.check_obj_in_receptacle(obj, receptacle)` utility: that
function accepts any real MuJoCo contact within ~70% of the candidate
receptacle's horizontal radius, with no directional/containment check at
all. A pan tipped down to pour genuinely touches the plate and is
genuinely close to it horizontally, so `check_obj_in_receptacle('plate',
'vegetable_container')` returns `True` -- RoboCasa's own utility can't
distinguish "plate is resting inside the pan" from "pan is hovering
directly above the plate to pour into it." Once `plate` is wrongly in the
tracked-contents set, the pan's later tilt/separation from the plate
reads as `plate` "departing" the receptacle, firing a spurious
`skill_dump_onset` with `plate` as the departing content. Since `plate`
has no liquid/solid food attributes, `dump_content_kind_for_preconditions`
resolves to `None`, and `_dump_support_type_matches_content` falls through
to its final `return False` -- entirely unrelated to any real
support-type problem, despite the misleading "support type doesn't match"
wording.

An initial attempted fix (`_dump_target_kind_name`, meant to prefer the
task's known intended receiving object over `_infer_support`'s
height-gated resting-support inference) was tried first, based on a
wrong diagnosis, then reverted once direct data inspection showed
`sup_kind`/`sup_name` were already correctly `object`/`plate` at all
three violation frames -- that fix was inert for this bug and added
unneeded complexity, so it was removed entirely rather than left in as
dead-but-harmless code.

**Fix.** In the content-tracking block (`monitor/sim/robocasa/
predicates.py`, ~line 6851, right before the loop that builds `tracked`
via `_content_receptacle_overlap`), exclude the active receptacle's own
known pour destination (`active_target_object_names`) from ever being
added to the tracked-contents set:
```python
tracked |= {
    str(name)
    for name in all_object_names
    if str(name) != str(active_object)
    and str(name) not in active_target_object_names
    and _content_receptacle_overlap(str(name), str(active_object))
}
```
A receptacle's own pour target is already known independently and is
structurally what content will end up *on*, never something carried
*inside* the receptacle doing the pouring -- so it should never become a
tracked-content candidate at all, regardless of what the generic
contact-based support check reports.

**Verified via re-extraction** (job 3855615): all three episodes now
report `0 violated / 20 satisfied` (down from 1 violated each). For
PanTransfer ep4 specifically, the fix collapsed what had been *two*
dump-onset firings (a real one plus the spurious `plate` one at frame
331) into a single, clean, correct onset for `vegetable` at frame 302.
(Note: the originally-disputed frame 276 for this same episode was
already resolved by item 2's grace-fallback scoping, prior to this
session's investigation -- it is unrelated to this fix.)
