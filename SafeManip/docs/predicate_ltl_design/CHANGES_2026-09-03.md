# Changelog — 2026-09-03: comprehensive KNOWN_BUGS fix pass on the `claude` branch

Context: the `claude` branch was created from `dev` at `6dae711` to hold a comprehensive
review/fix pass across all 19 LTL properties and their predicates, following the
`predicate-design-cycle` skill's methodology. Goal: fix every open, well-scoped
predicate-design bug in `KNOWN_BUGS.md`, then validate corpus-wide via a 50-task
x 10-episode scaled extraction, and populate a first-pass "claude" ground-truth
annotation draft for every episode.

## 1. `skill_pick_onset`: added the missing `object_is_manipulable` check (KNOWN_BUGS #1)

**Problem:** `action_onset_safety.txt`'s spec requires `object_is_manipulable` as one of
`skill_pick_onset`'s persisting AND-conditions; the code never checked it at all, so the
onset could fire on any nearby object the gripper approached, including non-manipulable ones.

**Fix:** added `_object_is_manipulable(name)`, grounded in the object's real MuJoCo joint
type -- a body with no joint (rigidly welded to its parent/world) cannot be manipulated
regardless of what a category-lookup table claims. Deliberately *not* based on
`attributes.py`'s `"graspable"` attribute, which is added unconditionally to every single
object category (`object_category_attribute_defaults`'s last line runs with no gating
condition) and so can never discriminate a genuinely non-manipulable object -- using it would
have been a no-op, not a fix. Wired into `pick_onset_cond` as an additional AND term.

**Confidence:** medium -- physically well-grounded (same "check what the sim itself actually
represents" approach as the mesh-distance `mj_geomDistance` upgrade), but not yet spot-checked
against a confirmed real non-manipulable object in this corpus (unclear how often a
genuinely non-free-jointed "object" entry actually appears in `env_object_names` in practice).

## 2. `skill_dump_onset`: removed the inverted tilt requirement (KNOWN_BUGS #2)

**Problem:** `action_onset_safety.txt`/`containment_safety.txt` explicitly say dump onset
must not be gated on receptacle tilt or loss of uprightness "alone" -- uprightness should be
neither necessary nor sufficient. The code required `not grasped_receptacle_is_upright` as a
hard AND term, making persistent tilt a *necessary* gate -- exactly the behavior the spec
forbids. Concrete failure: content scooped out with a utensil or poured through a spout
without ever tilting past the grace threshold went completely un-monitored.

**Fix:** removed the `not grasped_receptacle_is_upright` term from `skill_dump_onset`'s
formula. `dump_onset_count`/`dump_left_content_names` (built from actual content-membership
diffing against `raw_dump_left_content_set`, not from tilt) already are the real "content
left the grasped receptacle" signal the spec wants. `grasped_receptacle_is_upright`'s own
computation and export are left intact as diagnostic context, just no longer gate onset.

## 4. Generalized hardcoded fruit/veg/colander/pot name checks (KNOWN_BUGS #4)

**Problem:** `run_monitor_on_privileged.py`'s clean-content/active-container classification
used hardcoded name-prefix/literal matches (`"fruit"`/`"veg"`/`"vegetable"`/`"colander"`/
`"pot"`) instead of the general tag/attribute lookup helpers that already existed elsewhere
in the monitor -- any container/content pair using different object names wouldn't generalize.

**Fix:** replaced with `entity_has_attribute` (already in `monitor/primitives.py`) checking
`"fruit"`/`"vegetable"`/`"receptacle"` -- real, populated, robocasa-native-tag-backed
attributes (confirmed not dead code via the `attribute_diff` tooling), not invented.
`static_info` threaded through `_repair_forbidden_contact_active_object_pairs` as a new
parameter so `entity_has_attribute` can resolve real object categories instead of falling
back to guessing from the bare instance name (which was the only option available before,
since only `dynamic_info` was in scope at this call site).

**Verified:** against real `ArrangeBreadBasket` data -- `basket` correctly resolves as
`receptacle=True`, `bread` as `fruit=False`/`receptacle=False`.

## 6. Fixed `rc_released_object_eventually_settles`'s temporal-evidence mispairing (KNOWN_BUGS #6)

**Problem:** the violation explanation builder picked the *first* `object_released=True`
frame in the whole episode, then the *first* `object_settled=True` frame anywhere after it --
neither checked they belonged to the same release/settle watch cycle. Since
`object_released`/`object_settled` are single global predicates (one settle-watch slot,
reassigned on each new release), a later, unrelated object's settle event could get
misattributed to an earlier, different object's violation, making the explanation read "it
eventually settled, just late" when the originally-violated object never settled at all.

**Fix:** anchored on `object_release_frame`, a per-frame field `predicates.py` already
tracks precisely for this purpose (`evidence_release_frame = settle_release_frame`, reset on
every genuine `object_released` edge, held steady in between) -- read directly from the
trap-confirmation frame's own `violation_evidence`, no re-derivation needed. The
settle-search now also stops the instant `object_release_frame`'s value changes (a new
release cycle started), so a later cycle's settle can never leak into an earlier one's
explanation.

**Verified:** a synthetic two-cycle test reproducing the exact original bug (confirmed the
old logic mispairs; the new logic correctly returns "never settled" for the first cycle) plus
a real end-to-end monitor rerun (`ArrangeBreadBasket` ep1) with no crash.

## 9. `_support_stable()`/`_target_stable()`: switched to relative stability (KNOWN_BUGS #9)

**Problem:** both used world-frame `_object_stable`/`persistent_object_stable_by_name`
instead of `_object_stable_relative` -- the same false-positive shape already fixed for
`object_settled` (a support/target currently being carried has nonzero world-frame velocity
even while genuinely at rest relative to its carrier, e.g. stacking `bowl2` onto `bowl1`
while `bowl1` is still in-hand).

**Fix:** both switched to `_object_stable_relative(name)`, matching `object_settled`'s
existing precedent exactly.

## 11. `_object_aabb()`: fixed the stale-bounding-box-while-held bug (KNOWN_BUGS #11)

**Problem:** `_object_aabb()`'s fallback order tried `_object_ou_bbox_aabb` (upstream
robocasa's `env.objects[name].get_bbox_points(trans=body_xpos, rot=body_xquat)`) first, and
whenever it returned anything at all, every one of `_object_aabb()`'s ~25 callers got that
value. Confirmed via frame-by-frame debugging (`ArrangeBreadBasket` ep7, frames 710-718,
`basket` actively grasped) that this returns a stale/offset box that doesn't track the
object's real current extent while held.

**Fix:** flipped the fallback priority to try `_object_contact_aabb` (built from the
object's own live contact-geom positions, the same primitive `object_left_gripper` and the
mesh-distance `gripper_away_from_object` tiering already trust) first, keeping
`_object_ou_bbox_aabb` only as a last-resort fallback. Since this is upstream robocasa's own
`get_bbox_points()`, not something SafeManip can fix directly, changing the fallback order in
our own wrapper is the right fix, not patching upstream.

**Confidence:** high for the code-level bug and the confirmed case (`basket`, held); the fix
itself is architectural (a static rest-pose box composed with the current body transform,
not a per-object mesh issue) rather than basket-specific, but not yet independently
re-verified for every object/task -- the 50-task x 10-episode scaled validation below is the
first broad check of this.

## 10. All remaining `recovery_ltl` bare-atom bugs fixed -- bug #10 now fully resolved

Fixed the last 3 properties still affected by the bare-atomic-proposition bug documented in
`KNOWN_BUGS.md` #10 (already fixed for 2 properties on 2026-09-02):

- `rc_fixture_open_obstacle_retract`: `"fixture_fully_closed"` -> `"F(fixture_fully_closed)"`.
- `rc_fixture_close_obstacle_retract`: `"fixture_fully_open"` -> `"F(fixture_fully_open)"`.
- `rc_microwave_single_object_until_empty`: `"!two_or_more_objects_in_microwave"` ->
  `"F(microwave_empty)"` -- needed a different target atom, not just an `F(...)` wrap: the
  original escape term was a genuine tautological-escape-term bug (Bug B, see
  `recovery-ltl-design`), already `True` at the trap frame whenever the violation involves
  exactly 1 object present (not 2+), which would have resolved recovery instantly for that
  violation shape regardless of whether the microwave was ever actually emptied. Retargeted
  to `microwave_empty` -- the main formula's own genuine resolve atom, matching the pattern
  used for the fixture properties above.

All three verified via isolated `LTLfDFA` tests: never tautologically satisfied at the
trap-confirmation frame, in every violation shape checked (including the 1-object vs. 2+-object
distinction for the microwave case).

## Annotation schema: claude/human x gt_annotation/monitor_problem

Implemented the schema designed in `.claude/skills/ltl-ground-truth-annotation/SKILL.md`:
`viewer/server.py`'s `save_annotations()` gained an additive `source` ("claude"/"human")
block per instance, holding `gt_annotation` (what actually happened) separately from
`monitor_problem` (whether the monitor's own reasoning was sound) -- backward compatible with
the existing flat `verdict`/`note`/`ai_draft` fields.

`SafeManip/monitor/populate_claude_annotations.py`: batch-populates the "claude" block for
every instance of every episode in a scaled extraction, reusing `viewer/server.py`'s own
`load_monitor_view` (the exact code path the viewer itself uses) rather than re-deriving
anything. Explicitly labeled as an automated first-pass draft (monitor-derived, not
independently frame-by-frame re-verified against raw sim state) -- honest about the
difference given the corpus scale (500 episodes x ~20 instances each). `monitor_problem` is
flagged `has_problem=True` with a corpus-wide caveat (not a per-instance finding) for
properties that read fixture identity, given `KNOWN_BUGS.md` #7's confirmed ~89%-of-episodes
static/dynamic fixture-naming mismatch (an upstream data issue, unresolved, outside
`SafeManip/`).

## Two more bugs found via scaled-test investigation (Phase 4/5 of predicate-design-cycle)

Continued digging into the properties flagged as "not yet investigated" above:

- **`specs.py`/`predicates.py` `SETTLE_TIMEOUT_FRAMES` drift**: `specs.py` had its own
  independent, hardcoded `SETTLE_TIMEOUT_FRAMES = 6`, never updated when `predicates.py`'s
  copy was changed to 50 then 100 earlier this session. Produced genuinely misleading
  explanation text (e.g. "timeout at frame 351" on a violation whose real trap wasn't
  confirmed until frame 444 -- 99 frames later, using the correct value); the real
  violated/satisfied verdict was unaffected. Fixed by having `specs.py` import the constant
  directly from `monitor.sim.robocasa.predicates` instead of duplicating it -- single source
  of truth.
- **`_support_type_matches()`'s missing interior-vs-structural distinction** -- root cause of
  `rc_place_preconditions_safe`'s 100% violation rate on `CategorizeCondiments`. The spec
  defines "structural fixture body" as specifically door/frame/drawer-body
  (`action_onset_safety.txt:486-487`), not a fixture's interior shelf, but the code treated
  *any* fixture support as automatically incompatible for food objects. Fixed by reusing
  `_fixture_interior_support_aabb` (already existed, real robocasa interior-region metadata)
  to recognize genuine shelf placement as compatible. **Verified via real re-extraction**
  (`CategorizeCondiments` ep0): `rc_place_preconditions_safe` flips from violated to satisfied,
  with the other two independently-diagnosed violations for that episode (`rc_no_forbidden_contact`,
  `rc_released_object_eventually_settles`) correctly unaffected.

**Diagnosed but not yet fixed**: the dump-transfer "receiver" field
(`predicates.py`, the `elif skill_dump_onset and active_object is not None:` branch,
`"receiver_kind": sup_kind, "receiver_name": sup_name`) reuses the generic "what currently
supports the active/grasped object" variable instead of the actual dump destination -- since
the source receptacle is actively held (in-hand, no real physical support), this can produce
spurious results, e.g. a `SteamInMicrowave` vegetable's landing surface recorded as
`"floor_room"`. Plausibly a real contributor to `rc_solid_transfer_eventually_settles`'s
elevated rate. Not fixed yet -- needs to confirm which variable correctly represents the real
dump target (candidates seen elsewhere: `target_fixture_names`/`action_target_fixtures`) before
substituting it, to avoid a wrong fix.

A full re-run of the 50-task x 10-episode scaled validation (SLURM job 3748063, output to
`monitor/output/v6_2026-09-03_claude_branch_settle_and_support_type_fixes/`) confirmed both
fixes: **overall violation rate 729/10000 (7.29%)**, down from v5's 741/10000 (7.41%).
`rc_place_preconditions_safe` dropped from 75 to 65 instances, all of it from
`CategorizeCondiments` (10/10 episodes -> 0/10 episodes for this property specifically, exactly
as predicted). `SETTLE_TIMEOUT_FRAMES` drift fix doesn't change any verdict by design (display
text only), so no count change from that half. Other properties unchanged, as expected -- these
two fixes were narrowly scoped to their specific confirmed root causes, not blanket changes.

### Dump-transfer destination tracking: diagnosed, not fixed (architectural gap, not a quick patch)

Investigated further why the dump-transfer "receiver" can read as something physically
implausible (e.g. a vegetable's landing surface recorded as `"floor_room"` in a microwave-
steaming task). Root cause: there is no single, dedicated "what is this dump actually landing
on" concept in the code -- multiple different call sites each reuse a *different* generic
variable that was designed for something else:
- `active_transfer["receiver_name"]` (predicates.py, the `elif skill_dump_onset...:` branch)
  reuses `sup_kind`/`sup_name` -- "what currently supports the active/grasped object" (correct
  for stability/support-type checks elsewhere, but the actively-*held* source receptacle
  typically has no real physical support of its own, so this can fall back to something
  physically implausible like the room floor).
- The generic onset-explanation builder (`run_monitor_on_privileged.py:1092-1100`, shared
  across every `INTENDED_SAFETY_PROPERTY_ACTIONS` property) reuses `evidence["active_target"]`/
  `evidence["approach_target"]` -- a generic "most recently active fixture interaction" field
  that gets set by whichever skill-onset (open_close, press, dump, ...) most recently touched a
  fixture, not something dump-specific either (explains labels like
  `'fixture:fridge_main_group:open_close'` showing up as a *dump* onset's own target text).

Both are real, plausible contributors to `rc_dump_preconditions_safe`/
`rc_solid_transfer_eventually_settles`'s elevated rates, but fixing either correctly means
introducing a genuinely new "actual dump destination" concept (tracking where the content is
really landing, independent of what supports the still-grasped source receptacle or whatever
fixture some other skill last touched) -- not a small, safely-scoped patch like the two fixes
above. Given how central and widely-shared `sup_kind`/`sup_name` and the generic onset-target
fields are, a rushed substitution risks a regression elsewhere. Left as a diagnosed, well-scoped
follow-up needing dedicated design work, not attempted here.

### Remaining path to "very low" violation rate needs product/design decisions, not more autonomous fixing

At this point the largest remaining contributors to the corpus-wide rate are not further
hidden code bugs of the kind fixed above -- they're either genuine task/demo behavior correctly
caught by a strict property, or a documented pre-existing feature gap:
- `rc_no_forbidden_contact` (35.8%): confirmed genuine incidental contact with unrelated
  furniture during normal reach motions -- a **policy question** (should minor incidental
  contact count against a "safe" demo?), not a defect.
- `rc_raw_robot_contact_blocks_rte_grasp_until_sanitized` (12.8%): root-caused to
  `sanitized = False` being hardcoded -- and the spec **already documents this as deliberate**.
  Implementing real sanitization detection is a new feature (what should "sanitized" mean?),
  not a fix.
- `rc_fixture_open_obstacle_retract`/`rc_fixture_close_obstacle_retract` (9.4%/12.8%):
  plausibly downstream of the confirmed, unresolved upstream fixture-naming data issue
  (KNOWN_BUGS.md #7, ~89% of episodes) -- not fixable in `SafeManip/`.
- `rc_dump_preconditions_safe`/`rc_solid_transfer_eventually_settles` (13.8%/11.2%): partially
  explained by the dump-destination-tracking architectural gap above (needs dedicated design
  work, not a quick fix) and partially by the spec's own deliberate "solid content requires an
  object/receptacle receiver" rule correctly catching demos that place food loose into a
  fixture (e.g. directly into a microwave) without a container -- also arguably a policy
  question, not a bug.

Getting meaningfully below the current ~7.3% would require the user's decisions on the policy
questions above and/or a dedicated follow-on design effort for dump-destination tracking --
not more autonomous guessing at what the "right" fix should be for genuinely ambiguous cases.

**v17 is the largest single-version drop this session on both metrics** (2.62%->1.56% instance,
40.60%->19.20% episode excl. forbidden-contact -- more than halved). Two distinct, previously-
undiagnosed bugs, both found by systematically scanning the v16 corpus for `(task, property)` pairs
where nearly all 10 independent episodes of a task violated the same property (see the new Phase
4.7 in `predicate-design-cycle`'s `SKILL.md`):
- **`_object_support_type_matches_any`** (settle-check for food-type objects) only ever checked
  *other objects* as possible supports, never fixtures at all, unlike its sibling
  `_object_supported_on_correct`. A food-type object resting directly on an ordinary fixture
  surface (a counter, cabinet interior -- e.g. `CategorizeCondiments`' condiments) could never
  satisfy this, so `object_settled` stayed permanently `False` even when genuinely, visibly at
  rest. Verified: `CategorizeCondiments` ep0 1 violated -> 0 violated.
- **`fixture_obstacle_contact`** counted any non-robot, non-fixture geom touching the active
  fixture as an obstacle, including objects the task deliberately places *inside* the fixture
  (food in a microwave/oven, dishes in a dishwasher rack) -- those sit in constant, legitimate
  contact with the fixture interior for the whole task, so any task whose premise is "put things
  inside this appliance" hit this every episode: `HeatKebabSandwich` (10/10 -> 0/174 instances),
  `LoadDishwasher` (8/10 -> 0/164 instances).
- **`rc_fixture_{open,close}_obstacle_retract`'s bare `U fixture_fully_{open,closed}` target**
  required the fixture to be driven all the way back to the opposite extreme, but real demos
  routinely just disengage from an obstacle and move on with the rest of the task without ever
  revisiting that fixture -- median observed gap between the last obstacle hit and episode end,
  across these cases, was 133 frames of doing something else entirely. Under finite-trace

## v19: `RecycleBottlesByType` fully resolved via an AST-visitor fix, not a predicate fix

Root cause traced further than v18 left it: `_manipulated_object_names`/`object_grasped` depend on
`_success_target_relations()`, which statically parses a task's `_check_success` source (via
`ast`/`inspect.getsource`) for literal object-name strings passed to 4 recognized robocasa
success-check API calls. `RecycleBottlesByType`'s real `_check_success` combines three patterns the
visitor didn't handle at all: a plain `bottles = self.objects[...]`-style variable assignment (not
inline), list concatenation (`glass_bottles + plastic_bottles`, an `ast.BinOp` with `Add`), and a
generator-expression `for`-clause (`all(check_obj_fixture_contact(env, b, bin) for b in bottles)`)
-- all three needed together, so nothing at all was recognized and `object_grasped` silently never
fired for this task's whole 10-episode set.

**Fix:** extended `_literal_string_set()` to handle `ast.BinOp(Add)` (list concatenation), and
replaced the visitor's raw per-statement iteration with a `visit_body(stmts, bindings)` helper that
threads a mutable name->value bindings dict through a statement list in program order (so a plain
single-`Name`-target `ast.Assign` earlier in the function is resolvable when referenced later), used
consistently for function/module bodies, `for`-loop bodies, and -- new -- generator/comprehension
`.generators` clauses (`ast.GeneratorExp`/`ListComp`/`SetComp`/`DictComp`, each walked via its
`ast.comprehension` nodes' `.target`/`.iter`/`.ifs`).

**Verified:** dry-ran the new AST logic directly against the real robocasa `RecycleBottlesByType`
source before touching the shared production file; then re-extracted the target task (3 spot-check
episodes, `object_grasped` firing correctly) plus 2 unrelated regression-check tasks (`ArrangeBreadBasket`,
`StackBowlsCabinet`) confirmed byte-for-byte unchanged; then a full corpus-wide `>=5/10` scan
confirmed `RecycleBottlesByType` completely off the list (was 8/10 in v18, the last remaining
non-sanitization/non-StackBowlsCabinet entry). A v18-vs-v19 full-corpus diff of violated-episode
sets per `(task, property)` found exactly one single-episode regression --
`HeatKebabSandwich`/`rc_fixture_open_obstacle_retract` (0 -> 1) -- consistent with the

### v9: two more bugs found in that remaining 94/500 bucket

Found via the same systematic clustering, applied to v8's remaining unexplained 94/500 episodes:

1. **`_fixture_open_fraction` max-not-mean fix.** Upstream robocasa's default
   `door_joint_names` property returns *every* joint whose name contains "door" for a
   fixture -- for a compound fixture like a fridge, that's both the fridge-compartment
   door joint AND the independent freezer-compartment door joint.
   `_fixture_open_fraction` averaged their (already correctly 0-1-normalized, via
   `Fixture.get_joint_state`) values, so opening only the fridge door (norm ~1.0) while
   the unrelated freezer door stayed closed (norm ~0.0) produced an averaged fraction
   (~0.5-0.74 depending on episode) well below `FIXTURE_FULLY_OPEN_FRACTION` (0.90) --
   falsely reporting "not fully open" for `rc_reach_in_fixture_only_when_fully_open` even
   though the compartment actually entered was wide open the whole time. Confirmed
   corpus-wide: 100% (10/10 episodes) of `PackIdenticalLunches`' violations for this
   property showed the exact same signature (gripper entering `fridge_{main,left,right}_
   group` at frame 24-38, `fixture_fully_open` reading False despite the relevant door's
   joint being open since frame 0). Fixed by using `max()` instead of `mean()` across a
   fixture's door joints -- "fully open" if *any* door is open past threshold, a no-op
   for single-door fixtures. Result: `rc_reach_in_fixture_only_when_fully_open` 25/500 ->
   4/500 violated instances.
2. **`rc_grasp_remains_synced_until_dropped` weak-until fix.** The formula used strict
   `U` (`object_sync U object_dropped`), which asserts a *liveness* guarantee
   ("`object_dropped` eventually becomes true") -- but this is meant to be a *safety*
   property ("stays synced for as long as it's held"). A demo that legitimately ends
   still holding the object (task success reached without ever needing to release it)
   can never satisfy "eventually dropped" within a finite trace, so LTLf's finite-trace
   semantics flagged it as a permanent violation purely because the recording stopped
   mid-grasp. Confirmed corpus-wide: 100% (10/10 episodes) of `WashLettuce`'s violations
   for this property were `object_grasped=True, object_sync=True, object_dropped=False`
   at the *exact last frame* of the episode (verified across 10 different episode
   lengths, 372-581 frames) -- not a slip event at all. Fixed by switching to weak
   until (`(object_sync U object_dropped) | G(object_sync)`, since this LTLf grammar has
   no native `W`/`R` operator): either eventually dropped while having stayed synced the
   whole time, or stays synced for the rest of the trace without ever needing to
   resolve. Result: `rc_grasp_remains_synced_until_dropped` 18/500 -> 8/500 violated
   instances.

**v9 net effect:** instance-level 5.51% -> 5.20%; episode-level-excluding-`rc_no_

### Infra: monitor-only reruns can reuse the per-episode SLURM pipeline too

A `specs.py`/`predicates.py` change that only affects monitor-time LTL evaluation (not
extraction) doesn't need re-extraction -- but running the monitor-only rerun serially in
one process is still slow (each call loads a full 100-170MB `privileged_information_
<N>.json`; a serial pass over 500 episodes took 2.5+ hours for only 320/500). Built
`rerun_monitor_only.py --task T --episode N` (single-pair mode, mirroring `extract_
privileged_from_dataset.py`) plus `run_rerun_monitor_only_per_episode.sbatch` /
`submit_rerun_monitor_only_per_episode.sh`, reusing the exact same per-(task,episode)-
array-index pattern as the extraction pipeline. The submit script also only enqueues
pairs whose `_monitor.json` is missing or older than `predicates.py`/`specs.py`'s mtime,
so a follow-up rerun after a small fix doesn't redo already-current episodes (confirmed
useful in practice: only 64/500 needed rerun after the grasp-sync fix, since most of
v9's extraction array tasks hadn't started their monitor step yet when that fix landed
and picked it up automatically).

**v0's `rc_grasp_remains_safe_until_release` vs. its v6+ split-equivalent** (the "redesign, not
smoothing" reference case): v0 had 132/500 episodes violated (26.4%) for the single original
property; the like-for-like comparison at v6+ (an episode counted as violated if *either*
`rc_grasp_remains_synced_until_dropped` or `rc_dropped_object_was_released` fires) is 30/500
(6.0%) -- an ~80% reduction from the `object_sync`/bilateral-contact redesign alone, done before
this session. This is the calibration reference for "what a genuine structural redesign can
achieve" cited throughout this changelog and in `predicate-design-cycle`'s Phase 4.6.

**Why v0 -> v6's rate went up, not down, despite real bug fixes landing in between:** several
changes made detection *more complete/sensitive* rather than looser, which mechanically raises
the raw violated count even when working correctly -- most notably the KNOWN_BUGS #2 tilt-gate
removal (made `rc_dump_preconditions_safe` go from 2 to 64-69 violated instances by correctly
firing on previously-silently-suppressed real dump onsets) and earlier debounce-removal work on
fixture-obstacle-contact detection (made `rc_fixture_{open,close}_obstacle_retract` far more
sensitive to real, brief contact events that a coarser detector would have missed entirely).

**Why v6 -> v7's rate barely moved despite a real, verified bug fix
(`fixture_{open,close}_retracting`'s self-contradiction):** checked directly -- every instance
that violated under the old, structurally-unsatisfiable definition is *also* genuinely violated
under the fixed one (64/64, 47/47 for close/open respectively). Real per-episode obstacle-hit-to-
retract delay was measured directly and is genuinely variable (1 to 47 frames across a handful of
spot-checked episodes/tasks) -- not a fixed monitoring artifact, confirming this is real signal
(some demos genuinely take over 2 seconds to back off from a hit obstacle), not a bug the fix
should have eliminated. A small (1-2 frame) grace period for genuine control-loop reaction latency
is a plausible, principled refinement worth considering separately, but would only affect the
shortest-delay instances -- the double-digit-frame delays are real, substantial, and should stay
flagged.

Attempted a small (7-frame) grace period on `fixture_{open,close}_retracting`'s obligation, based

(2-7 frames clustered, then a jump to 14+). Implemented, then verified directly against a real
episode (`DeliverStraw` ep2) via debug instrumentation -- and found `duration_frames` does **not**
measure the same thing as the raw `fixture_open_obstacle_hit` true-run length: the real per-frame
hit in that episode lasted 9 frames, not the 2 `duration_frames` reported. Redid the clustering
directly from the full per-frame `trace` (not the summary field) across the whole v9 corpus: real
raw hit-duration run-lengths are a smooth, continuous decay (65% at 1-3 frames, then a gradual
tail out past 79 frames) with **no natural cluster/gap** the way `SKILL_ONSET_FRAMES`/
`PERSISTENCE_FRAMES` had. There's no principled point in that distribution to call "genuine
reaction latency" vs. "real, substantial delay" -- any cutoff would be an arbitrary number
dressed up as evidence-grounded, which the no-shortcuts principle rules out. Reverted the change
entirely (confirmed `predicates.py` is byte-identical to the v9 commit afterward) rather than ship
an unjustified constant. This property's rate is now, like `rc_no_forbidden_contact`, a genuine
open policy question without a clean data-driven answer -- deferred pending a decision on what
counts as "reasonable" reaction time, if any grace is wanted at all.

## Diagnosed but not yet fixed: onset-instant support-type checks race physics settling
(rc_place_preconditions_safe AND rc_dump_preconditions_safe)

Found via clustering `rc_place_preconditions_safe`'s 24 violated instances (v9): `LoadDishwasher`
has 3/24 that all share the identical signature -- `dish0`/`dish1` placed onto `dishwasher_main_
group`, but `inferred_support_name` reads `floor_room` and `support_type_mismatch_reason` fires
("food object on structural fixture body"). This is very likely a false positive, not a real
placement onto the floor.

**Confirmed this is a shared root cause, not a place-specific one**: `rc_dump_preconditions_safe`'s
`PanTransfer` ep2 violation shows the identical pattern -- `object_supported_settle = False` at
the violating frame, and `inferred_support_name` reads `plate` (the dumped content's *own*
container -- a nonsensical, self-referential support reading, clearly a mid-motion snapshot
artifact, not a real "dumped plate onto itself"). Both properties fire their onset-triggered
precondition check off a raw, instantaneous event (`object_released` for place;
`skill_dump_onset` similarly instant for dump) before the object has physically settled --
`rc_pick_preconditions_safe`/`rc_twist_preconditions_safe` likely share the same architecture and
are worth checking too, though not yet confirmed against real violated instances.

Root cause, as far as diagnosed: `place_onset_cond = object_released` (`predicates.py:3505`) --
the place-safety-precondition check runs at the *exact instant* the gripper releases the object,
before physics has settled it onto its actual target (`object_supported_settle = False` at the
violating frame in all 3 cases, confirmed via `first_non_accepting_violation_evidence`).
`_infer_support`'s nearest-candidate scoring (predicates.py ~3593) evaluates the object's
instantaneous position against every candidate support's aabb; `_fixture_support_aabb`'s
dishwasher-specific path (`_fixture_rack_aabb`, using rack/tray joint geometry) can plausibly
return `None` if the object isn't yet positioned within/near the detected rack region at that
exact release instant -- falling through to the whole-fixture aabb, and if even that doesn't
register as close enough yet, `floor_room` (whose aabb spans the entire room, always the nearest
candidate by default) wins.

**Ruled out**: checked `privileged_static_info`'s `scene_layout.fixtures` for stray/missing
geometry data (`local_bounds_sites`, `quaternion`) as a KNOWN_BUGS #7-adjacent upstream data gap
-- both fields are `None`/all-zero for essentially *every* fixture in the corpus (not
dishwasher-specific), confirming this static-info snapshot isn't what `_fixture_support_aabb`
actually queries (that comes from live MuJoCo body/geom queries via `env.sim`, not this
descriptive metadata) -- a dead end, not the real cause.

**Not yet implemented**: the likely correct fix is evaluating the support-type-match check once
`object_supported_settle` becomes `True` rather than at the raw release instant -- but this
changes *when* a place-onset's preconditions are judged (a real timing-semantics decision, not a
one-line correction), and this session already reverted two speculative fixes after verification
disproved their premise (the grasp-bridge fix and the retract-grace period, both above/in
`BILATERAL_CONTACT_FLICKER_BUG.md`). Diagnosing to this level of confidence without a confirmed,
verified fix in hand, rather than risk a third unverified change -- flagged here for the next
session to implement and verify against real re-extracted data before considering it done.

## Investigated, inconclusive: SETTLE_TIMEOUT_FRAMES (rc_released_object_eventually_settles)

Checked whether this property's 100-frame timeout has the same "no clean cutoff" shape as
forbidden-contact/retract, or a genuine evidence-based one worth raising. `repeated_violation_
episodes[i]["duration_frames"]` is unreliable here too (all exactly `2`, clearly not real settle
latency -- same class of misleading-summary-field issue as the two earlier reverted/corrected
investigations this session).

Spot-checked one real case directly: `SearingMeat` ep5's `pan`, released at frame 118, times out
at 218 (100 frames later). Initially looked like a simple "settles late" case -- `object_settled`
does read `True` briefly at frames 298-308 and again at 423-432 -- but the violation's own final
evidence says the property considers it unsettled all the way to the episode's last frame (528),
and `settle_obj_name` had already moved on to tracking a *different* object (`meat`) by then. So
this isn't "takes 180 frames to settle once and stay settled" -- the pan's settled state flickers
True then reverts False again, meaning it's genuinely being disturbed repeatedly (plausible for a
pan actively used through a searing/cooking sequence), not just slow to reach one stable rest
state. Raising `SETTLE_TIMEOUT_FRAMES` wouldn't fully address this specific pattern even if it
were the fix for *other* slow-but-monotonic cases.

Attempted a corpus-wide version of this measurement (real release -> first-subsequent-settled
latency, scanning each violated instance's full per-frame trace) but the result was inconclusive
for the same multi-object reason: `object_released`/`object_settled` are generic per-frame
booleans keyed to whatever `settle_obj_name` is currently being watched, which can silently swap
to a different, later-released object before the original one is resolved -- so a naive scan
picks up the wrong object's cycle in episodes with multiple releases (confirmed: `settle_obj_name`
read `meat`, not `pan`, in the SearingMeat ep5 evidence above). **Not fixed, not reverted (nothing
was changed) -- flagged as a harder, two-part question for next time**: (1) does raising the
timeout help the genuinely-slow-but-monotonic cases, and (2) is the "gets disturbed and never
truly settles" pattern (like this pan) something the monitor should tolerate differently, or a
real signal worth keeping. Needs per-object-name-scoped trace analysis (not just the generic
`object_released`/`object_settled` booleans) to separate the two cleanly.

## Resolved (v16): rc_twist_preconditions_safe's remaining 4 instances

Originally left unfixed (see git history for this section's earlier text) pending dedicated
investigation, separate from the place/pick/dump settle-timing pattern. That investigation found
the real cause: `_fixture_ready_for_twist`/`_fixture_ready_for_press` checked `"oven" in fclass`
*before* `"toaster" in fclass`. A `"ToasterOven"` fixture's class name, lowercased
(`"toasteroven"`), contains both substrings, so it always silently fell into the stricter oven
branch (`_fixture_closed(fname) and _heat_contents_ready(contents, {"cookable", "food"})`) instead
of its own toaster branch (`_heat_contents_ready(contents, {"toastable", "bread_food", "cookable",
"food"})`), regardless of the fixture's real type. This exactly explained the "1/4 instances
showing an unexplained inconsistency between the explanation text and the raw evidence field"
finding noted earlier: `_fixture_ready_failure_reason` (the explanation-text builder, a separate
function) already checked `"toaster"` before `"oven"` for press/twist, so the human-readable text
and the actual pass/fail verdict were computed via two different, disagreeing branches for the
same fixture. Verified directly: `kebab`/`baguette` (the toaster oven's real contents) both
genuinely have `food`/`cookable` attributes and should satisfy the toaster branch's own check.
Fixed by reordering both functions to check `"toaster"` before `"oven"`, matching
`_fixture_ready_failure_reason`'s already-correct order. Result: 4/500 -> 0/500 violated
instances.
