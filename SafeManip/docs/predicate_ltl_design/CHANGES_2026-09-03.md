# Changelog — 2026-09-03: comprehensive KNOWN_BUGS fix pass on the `claude` branch

Context: the `claude` branch was created from `dev` at `6dae711` to hold a comprehensive
review/fix pass across all 19 LTL properties and their predicates, following the
`predicate-design-cycle` skill's methodology. Goal: fix every open, well-scoped
predicate-design bug in `KNOWN_BUGS.md`, then validate corpus-wide via a 50-task
x 10-episode scaled extraction, and populate a first-pass "claude" ground-truth
annotation draft for every episode.

## 1. `skill_pick_onset`: added the missing `object_is_manipulable` check (KNOWN_BUGS #1)

**Problem:** `action_onset_safety.txt`'s spec requires `object_is_manipulable` as one of
`skill_pick_onset`'s persisting AND-conditions; the code never checked it at all, so the
onset could fire on any nearby object the gripper approached, including non-manipulable ones.

**Fix:** added `_object_is_manipulable(name)`, grounded in the object's real MuJoCo joint
type -- a body with no joint (rigidly welded to its parent/world) cannot be manipulated
regardless of what a category-lookup table claims. Deliberately *not* based on
`attributes.py`'s `"graspable"` attribute, which is added unconditionally to every single
object category (`object_category_attribute_defaults`'s last line runs with no gating
condition) and so can never discriminate a genuinely non-manipulable object -- using it would
have been a no-op, not a fix. Wired into `pick_onset_cond` as an additional AND term.

**Confidence:** medium -- physically well-grounded (same "check what the sim itself actually
represents" approach as the mesh-distance `mj_geomDistance` upgrade), but not yet spot-checked
against a confirmed real non-manipulable object in this corpus (unclear how often a
genuinely non-free-jointed "object" entry actually appears in `env_object_names` in practice).

## 2. `skill_dump_onset`: removed the inverted tilt requirement (KNOWN_BUGS #2)

**Problem:** `action_onset_safety.txt`/`containment_safety.txt` explicitly say dump onset
must not be gated on receptacle tilt or loss of uprightness "alone" -- uprightness should be
neither necessary nor sufficient. The code required `not grasped_receptacle_is_upright` as a
hard AND term, making persistent tilt a *necessary* gate -- exactly the behavior the spec
forbids. Concrete failure: content scooped out with a utensil or poured through a spout
without ever tilting past the grace threshold went completely un-monitored.

**Fix:** removed the `not grasped_receptacle_is_upright` term from `skill_dump_onset`'s
formula. `dump_onset_count`/`dump_left_content_names` (built from actual content-membership
diffing against `raw_dump_left_content_set`, not from tilt) already are the real "content
left the grasped receptacle" signal the spec wants. `grasped_receptacle_is_upright`'s own
computation and export are left intact as diagnostic context, just no longer gate onset.

## 4. Generalized hardcoded fruit/veg/colander/pot name checks (KNOWN_BUGS #4)

**Problem:** `run_monitor_on_privileged.py`'s clean-content/active-container classification
used hardcoded name-prefix/literal matches (`"fruit"`/`"veg"`/`"vegetable"`/`"colander"`/
`"pot"`) instead of the general tag/attribute lookup helpers that already existed elsewhere
in the monitor -- any container/content pair using different object names wouldn't generalize.

**Fix:** replaced with `entity_has_attribute` (already in `monitor/primitives.py`) checking
`"fruit"`/`"vegetable"`/`"receptacle"` -- real, populated, robocasa-native-tag-backed
attributes (confirmed not dead code via the `attribute_diff` tooling), not invented.
`static_info` threaded through `_repair_forbidden_contact_active_object_pairs` as a new
parameter so `entity_has_attribute` can resolve real object categories instead of falling
back to guessing from the bare instance name (which was the only option available before,
since only `dynamic_info` was in scope at this call site).

**Verified:** against real `ArrangeBreadBasket` data -- `basket` correctly resolves as
`receptacle=True`, `bread` as `fruit=False`/`receptacle=False`.

## 6. Fixed `rc_released_object_eventually_settles`'s temporal-evidence mispairing (KNOWN_BUGS #6)

**Problem:** the violation explanation builder picked the *first* `object_released=True`
frame in the whole episode, then the *first* `object_settled=True` frame anywhere after it --
neither checked they belonged to the same release/settle watch cycle. Since
`object_released`/`object_settled` are single global predicates (one settle-watch slot,
reassigned on each new release), a later, unrelated object's settle event could get
misattributed to an earlier, different object's violation, making the explanation read "it
eventually settled, just late" when the originally-violated object never settled at all.

**Fix:** anchored on `object_release_frame`, a per-frame field `predicates.py` already
tracks precisely for this purpose (`evidence_release_frame = settle_release_frame`, reset on
every genuine `object_released` edge, held steady in between) -- read directly from the
trap-confirmation frame's own `violation_evidence`, no re-derivation needed. The
settle-search now also stops the instant `object_release_frame`'s value changes (a new
release cycle started), so a later cycle's settle can never leak into an earlier one's
explanation.

**Verified:** a synthetic two-cycle test reproducing the exact original bug (confirmed the
old logic mispairs; the new logic correctly returns "never settled" for the first cycle) plus
a real end-to-end monitor rerun (`ArrangeBreadBasket` ep1) with no crash.

## 9. `_support_stable()`/`_target_stable()`: switched to relative stability (KNOWN_BUGS #9)

**Problem:** both used world-frame `_object_stable`/`persistent_object_stable_by_name`
instead of `_object_stable_relative` -- the same false-positive shape already fixed for
`object_settled` (a support/target currently being carried has nonzero world-frame velocity
even while genuinely at rest relative to its carrier, e.g. stacking `bowl2` onto `bowl1`
while `bowl1` is still in-hand).

**Fix:** both switched to `_object_stable_relative(name)`, matching `object_settled`'s
existing precedent exactly.

## 11. `_object_aabb()`: fixed the stale-bounding-box-while-held bug (KNOWN_BUGS #11)

**Problem:** `_object_aabb()`'s fallback order tried `_object_ou_bbox_aabb` (upstream
robocasa's `env.objects[name].get_bbox_points(trans=body_xpos, rot=body_xquat)`) first, and
whenever it returned anything at all, every one of `_object_aabb()`'s ~25 callers got that
value. Confirmed via frame-by-frame debugging (`ArrangeBreadBasket` ep7, frames 710-718,
`basket` actively grasped) that this returns a stale/offset box that doesn't track the
object's real current extent while held.

**Fix:** flipped the fallback priority to try `_object_contact_aabb` (built from the
object's own live contact-geom positions, the same primitive `object_left_gripper` and the
mesh-distance `gripper_away_from_object` tiering already trust) first, keeping
`_object_ou_bbox_aabb` only as a last-resort fallback. Since this is upstream robocasa's own
`get_bbox_points()`, not something SafeManip can fix directly, changing the fallback order in
our own wrapper is the right fix, not patching upstream.

**Confidence:** high for the code-level bug and the confirmed case (`basket`, held); the fix
itself is architectural (a static rest-pose box composed with the current body transform,
not a per-object mesh issue) rather than basket-specific, but not yet independently
re-verified for every object/task -- the 50-task x 10-episode scaled validation below is the
first broad check of this.

## 10. All remaining `recovery_ltl` bare-atom bugs fixed -- bug #10 now fully resolved

Fixed the last 3 properties still affected by the bare-atomic-proposition bug documented in
`KNOWN_BUGS.md` #10 (already fixed for 2 properties on 2026-09-02):

- `rc_fixture_open_obstacle_retract`: `"fixture_fully_closed"` -> `"F(fixture_fully_closed)"`.
- `rc_fixture_close_obstacle_retract`: `"fixture_fully_open"` -> `"F(fixture_fully_open)"`.
- `rc_microwave_single_object_until_empty`: `"!two_or_more_objects_in_microwave"` ->
  `"F(microwave_empty)"` -- needed a different target atom, not just an `F(...)` wrap: the
  original escape term was a genuine tautological-escape-term bug (Bug B, see
  `recovery-ltl-design`), already `True` at the trap frame whenever the violation involves
  exactly 1 object present (not 2+), which would have resolved recovery instantly for that
  violation shape regardless of whether the microwave was ever actually emptied. Retargeted
  to `microwave_empty` -- the main formula's own genuine resolve atom, matching the pattern
  used for the fixture properties above.

All three verified via isolated `LTLfDFA` tests: never tautologically satisfied at the
trap-confirmation frame, in every violation shape checked (including the 1-object vs. 2+-object
distinction for the microwave case).

## Annotation schema: claude/human x gt_annotation/monitor_problem

Implemented the schema designed in `.claude/skills/ltl-ground-truth-annotation/SKILL.md`:
`viewer/server.py`'s `save_annotations()` gained an additive `source` ("claude"/"human")
block per instance, holding `gt_annotation` (what actually happened) separately from
`monitor_problem` (whether the monitor's own reasoning was sound) -- backward compatible with
the existing flat `verdict`/`note`/`ai_draft` fields.

`SafeManip/monitor/populate_claude_annotations.py`: batch-populates the "claude" block for
every instance of every episode in a scaled extraction, reusing `viewer/server.py`'s own
`load_monitor_view` (the exact code path the viewer itself uses) rather than re-deriving
anything. Explicitly labeled as an automated first-pass draft (monitor-derived, not
independently frame-by-frame re-verified against raw sim state) -- honest about the
difference given the corpus scale (500 episodes x ~20 instances each). `monitor_problem` is
flagged `has_problem=True` with a corpus-wide caveat (not a per-instance finding) for
properties that read fixture identity, given `KNOWN_BUGS.md` #7's confirmed ~89%-of-episodes
static/dynamic fixture-naming mismatch (an upstream data issue, unresolved, outside
`SafeManip/`).

## Two more bugs found via scaled-test investigation (Phase 4/5 of predicate-design-cycle)

Continued digging into the properties flagged as "not yet investigated" above:

- **`specs.py`/`predicates.py` `SETTLE_TIMEOUT_FRAMES` drift**: `specs.py` had its own
  independent, hardcoded `SETTLE_TIMEOUT_FRAMES = 6`, never updated when `predicates.py`'s
  copy was changed to 50 then 100 earlier this session. Produced genuinely misleading
  explanation text (e.g. "timeout at frame 351" on a violation whose real trap wasn't
  confirmed until frame 444 -- 99 frames later, using the correct value); the real
  violated/satisfied verdict was unaffected. Fixed by having `specs.py` import the constant
  directly from `monitor.sim.robocasa.predicates` instead of duplicating it -- single source
  of truth.
- **`_support_type_matches()`'s missing interior-vs-structural distinction** -- root cause of
  `rc_place_preconditions_safe`'s 100% violation rate on `CategorizeCondiments`. The spec
  defines "structural fixture body" as specifically door/frame/drawer-body
  (`action_onset_safety.txt:486-487`), not a fixture's interior shelf, but the code treated
  *any* fixture support as automatically incompatible for food objects. Fixed by reusing
  `_fixture_interior_support_aabb` (already existed, real robocasa interior-region metadata)
  to recognize genuine shelf placement as compatible. **Verified via real re-extraction**
  (`CategorizeCondiments` ep0): `rc_place_preconditions_safe` flips from violated to satisfied,
  with the other two independently-diagnosed violations for that episode (`rc_no_forbidden_contact`,
  `rc_released_object_eventually_settles`) correctly unaffected.

**Diagnosed but not yet fixed**: the dump-transfer "receiver" field
(`predicates.py`, the `elif skill_dump_onset and active_object is not None:` branch,
`"receiver_kind": sup_kind, "receiver_name": sup_name`) reuses the generic "what currently
supports the active/grasped object" variable instead of the actual dump destination -- since
the source receptacle is actively held (in-hand, no real physical support), this can produce
spurious results, e.g. a `SteamInMicrowave` vegetable's landing surface recorded as
`"floor_room"`. Plausibly a real contributor to `rc_solid_transfer_eventually_settles`'s
elevated rate. Not fixed yet -- needs to confirm which variable correctly represents the real
dump target (candidates seen elsewhere: `target_fixture_names`/`action_target_fixtures`) before
substituting it, to avoid a wrong fix.

A full re-run of the 50-task x 10-episode scaled validation (SLURM job 3748063, output to
`monitor/output/v6_2026-09-03_claude_branch_settle_and_support_type_fixes/`) confirmed both
fixes: **overall violation rate 729/10000 (7.29%)**, down from v5's 741/10000 (7.41%).
`rc_place_preconditions_safe` dropped from 75 to 65 instances, all of it from
`CategorizeCondiments` (10/10 episodes -> 0/10 episodes for this property specifically, exactly
as predicted). `SETTLE_TIMEOUT_FRAMES` drift fix doesn't change any verdict by design (display
text only), so no count change from that half. Other properties unchanged, as expected -- these
two fixes were narrowly scoped to their specific confirmed root causes, not blanket changes.

### Dump-transfer destination tracking: diagnosed, not fixed (architectural gap, not a quick patch)

Investigated further why the dump-transfer "receiver" can read as something physically
implausible (e.g. a vegetable's landing surface recorded as `"floor_room"` in a microwave-
steaming task). Root cause: there is no single, dedicated "what is this dump actually landing
on" concept in the code -- multiple different call sites each reuse a *different* generic
variable that was designed for something else:
- `active_transfer["receiver_name"]` (predicates.py, the `elif skill_dump_onset...:` branch)
  reuses `sup_kind`/`sup_name` -- "what currently supports the active/grasped object" (correct
  for stability/support-type checks elsewhere, but the actively-*held* source receptacle
  typically has no real physical support of its own, so this can fall back to something
  physically implausible like the room floor).
- The generic onset-explanation builder (`run_monitor_on_privileged.py:1092-1100`, shared
  across every `INTENDED_SAFETY_PROPERTY_ACTIONS` property) reuses `evidence["active_target"]`/
  `evidence["approach_target"]` -- a generic "most recently active fixture interaction" field
  that gets set by whichever skill-onset (open_close, press, dump, ...) most recently touched a
  fixture, not something dump-specific either (explains labels like
  `'fixture:fridge_main_group:open_close'` showing up as a *dump* onset's own target text).

Both are real, plausible contributors to `rc_dump_preconditions_safe`/
`rc_solid_transfer_eventually_settles`'s elevated rates, but fixing either correctly means
introducing a genuinely new "actual dump destination" concept (tracking where the content is
really landing, independent of what supports the still-grasped source receptacle or whatever
fixture some other skill last touched) -- not a small, safely-scoped patch like the two fixes
above. Given how central and widely-shared `sup_kind`/`sup_name` and the generic onset-target
fields are, a rushed substitution risks a regression elsewhere. Left as a diagnosed, well-scoped
follow-up needing dedicated design work, not attempted here.

### Remaining path to "very low" violation rate needs product/design decisions, not more autonomous fixing

At this point the largest remaining contributors to the corpus-wide rate are not further
hidden code bugs of the kind fixed above -- they're either genuine task/demo behavior correctly
caught by a strict property, or a documented pre-existing feature gap:
- `rc_no_forbidden_contact` (35.8%): confirmed genuine incidental contact with unrelated
  furniture during normal reach motions -- a **policy question** (should minor incidental
  contact count against a "safe" demo?), not a defect.
- `rc_raw_robot_contact_blocks_rte_grasp_until_sanitized` (12.8%): root-caused to
  `sanitized = False` being hardcoded -- and the spec **already documents this as deliberate**.
  Implementing real sanitization detection is a new feature (what should "sanitized" mean?),
  not a fix.
- `rc_fixture_open_obstacle_retract`/`rc_fixture_close_obstacle_retract` (9.4%/12.8%):
  plausibly downstream of the confirmed, unresolved upstream fixture-naming data issue
  (KNOWN_BUGS.md #7, ~89% of episodes) -- not fixable in `SafeManip/`.
- `rc_dump_preconditions_safe`/`rc_solid_transfer_eventually_settles` (13.8%/11.2%): partially
  explained by the dump-destination-tracking architectural gap above (needs dedicated design
  work, not a quick fix) and partially by the spec's own deliberate "solid content requires an
  object/receptacle receiver" rule correctly catching demos that place food loose into a
  fixture (e.g. directly into a microwave) without a container -- also arguably a policy
  question, not a bug.

Getting meaningfully below the current ~7.3% would require the user's decisions on the policy
questions above and/or a dedicated follow-on design effort for dump-destination tracking --
not more autonomous guessing at what the "right" fix should be for genuinely ambiguous cases.
