# Changelog — 2026-08-31: grasp/settle robustness fixes

Context: the frame-count debounce constants in `predicates.py` (e.g.
`OBJECT_GRASPED_PERSISTENCE_FRAMES`, `RELATIVE_SPEED_PERSISTENCE_FRAMES`) were being used to
paper over two raw predicates that were measuring the wrong thing, rather than genuine sensor
noise. Debounce window size is inherently scenario-dependent (tuning it for one task breaks
another), so the fix here is at the raw-signal level instead of widening any buffers.

All changes are scoped to `SafeManip/monitor/sim/robocasa/predicates.py` (the SafeManip-side
copy) — the upstream `robocasa/` package (`robocasa/robocasa/environments/kitchen/predicates.py`)
was intentionally left untouched.

## 1. Grasp detection: bilateral contact instead of aggregate contact

**Problem:** `OU.check_obj_grasped` (upstream RoboCasa) treats the whole gripper as one geom
set — "does *any* gripper geom touch *any* object geom" — combined with a purely kinematic
"are both finger joints closed enough" check. Neither term requires *both* finger pads to be
touching the object at once. During the closing phase of a real grasp, one pad landing on the
object while the other is still open already satisfies this, causing spurious multi-frame
"grasped" flicker that the `OBJECT_GRASPED_PERSISTENCE_FRAMES` buffer was previously relied on
to filter out.

**Fix:** added `_object_gripper_bilateral_contact(name)`, which groups the gripper's contact
geoms by parent MuJoCo body (i.e. by finger) and requires `GRASP_BILATERAL_MIN_CONTACT_BODIES`
(=2) distinct finger bodies to be in contact with the object simultaneously — an antipodal-
contact precondition. Falls back to the old aggregate check for end-effectors that can't be
split into ≥2 distinct bodies (e.g. suction grippers). `_object_is_grasped` now ANDs this in
alongside the existing `OU.check_obj_grasped` call (tightening the raw signal, not replacing
it — bilateral contact implies aggregate contact, so no separate reimplementation of the
gripper-closed joint check was needed).

**New constant:** `GRASP_BILATERAL_MIN_CONTACT_BODIES = 2`

## 2. Grasp detection: distinguishing "touch" from "grasp" via eef velocity sync — tried, then reverted

**Problem:** bilateral contact + closed fingers still can't tell a real grasp apart from the
gripper merely pinching/pressing against an object that isn't actually coupled to it (e.g.
resting against it, or slipping loose as the arm moves) — both cases pass contact + closed
equally.

**Fix (initial):** `_object_is_grasped` was made to also require `_object_sync(name)` — the
object's velocity within tolerance of the end-effector's velocity (the same relative-velocity
check used downstream by `object_grasped_safe`). At rest this term is trivially satisfied (both
velocities ~0), so it mainly bit once the arm started moving, e.g. at lift-off, which is where
"touch vs. grasp" ambiguity matters.

**Refactor to avoid circularity (kept):** `_object_sync` used to internally call
`_object_is_grasped` to decide whether to use eef-relative or absolute-world-frame speed. Since
`_object_is_grasped` needed to call `_object_sync`, that circular dependency was removed:
`_object_sync` no longer has an internal grasp-state gate at all — it's purely "is this object's
velocity within tolerance of the eef's velocity," full stop. Callers (`object_grasped_safe`) are
responsible for combining it with `object_grasped` themselves; there is no separate "sync"
notion for a non-grasped object (that case is just `object_stable`). The externally-visible
predicate name/output key stays `object_sync` — this simplification is independent of item 2's
outcome below and was kept.

**Reverted:** folding `object_sync` into `object_grasped`'s own definition turned out to make
`object_grasped_safe` (`= object_grasped and object_sync`) a **logical tautology** — since
`object_grasped` already implied `object_sync`, `object_grasped_safe` was identically equal to
`object_grasped` on every frame (not just "usually the same due to matching debounce constants"
— provably the same value, always). That makes `G(object_grasped -> object_grasped_safe U
object_released)` permanently unable to distinguish "still grasped" from "still grasped but
unsafe," defeating the entire point of the property.

**Final decision:** `_object_is_grasped` is bilateral contact + closed fingers only again (no
`object_sync`); `object_sync` lives solely in `object_grasped_safe`, kept deliberately
independent so the two predicates can actually diverge. Accepted tradeoff, explicitly confirmed:
a bilateral, both-fingers-closed contact counts as a grasp on its own, even before the object
starts moving with the gripper — the original "touch vs. grasp" ambiguity this item set out to
fix is out of scope for now. `object_grasped_safe` is expected to catch the resulting
instability (desync) instead, once the arm starts moving.

A speed-based alternative (`object_grasped` requiring the object's own absolute speed be
nonzero, instead of eef-relative sync) was also tried and reverted in the same session: it broke
the common case of holding an object perfectly still (speed ~0 the whole time → `object_grasped`
would flip false during any stationary hold), which is worse than the problem it solved.

## 3. Settle stability: relative-to-support velocity instead of absolute world speed

**Problem:** `_object_stable` (used by `object_settled`) compared an object's absolute
world-frame speed against a fixed threshold. This produces false `release_object_settle_timeout`
violations when an object is placed inside a receptacle that is then itself picked up and
moved before the settle window elapses (e.g. bread placed in a basket, basket immediately
grasped and carried) — the bread is at rest *relative to the basket* the whole time, but its
absolute world speed tracks the basket's motion, so it never reads as "stable." This exact
failure mode is documented in `KNOWN_BUGS.md` bug #6 (`ArrangeBreadBasket` episode 0).

**Fix:** added `_object_stable_relative(name)`, which finds the object's current movable
support (via the existing `_current_support_contacts` machinery — fixtures are excluded and
still treated as stationary) and measures velocity relative to that support instead of the
world frame, falling back to absolute stability if there's no movable support. `object_settled`
now uses `_object_stable_relative` instead of `_object_stable`. This mirrors the pattern
`object_sync` already used relative to the end effector — same tolerances
(`OBJ_LINEAR_STABLE_THRESHOLD`, `OBJ_ANGULAR_STABLE_THRESHOLD`), same "subtract reference
velocity, threshold the residual" shape.

## 4. Same fix propagated to containment-transfer settle (liquid/solid dump/pour)

**Problem:** while auditing all 19 LTL properties end-to-end (see `LTL_PREDICATE_TREES.md`),
found that `content_stable` (used by `liquid_settled`/`solid_settled`, properties 7/8) still
used the plain absolute `_object_stable` per content item — the same carried-support
false-negative fixed in item 3 above could still occur here (e.g. dumping something into a
bowl, then picking up the bowl before the content's settle check completes).

**Fix:** `content_stable`'s per-content raw stability check now calls `_object_stable_relative`
instead of `_object_stable` (`predicates.py`, inside the containment-transfer settle logic).
No new constants; reuses the helper from item 3.

## 5. `object_released`: latched pending-release state instead of a single-frame check — tried, then reverted (2026-09-01)

**Problem:** `object_released` was `previously(object_grasped) and NOT object_grasped and
gripper_is_opening`. `object_grasped`'s own falling edge (bilateral contact / closed /
`object_sync` failing — e.g. down to one remaining finger contact) doesn't necessarily land on
the same frame as `check_contact(gripper, object)` actually reaching zero; full physical
separation can lag the smoothed grasp signal by an arbitrary number of frames. Concretely: frame
t, `object_grasped=True`; frame t+1, `object_grasped=False` but contact is still nonzero; frame
t+2, contact finally clears. At t+1 the release doesn't fire yet (contact still present, correct).
At t+2, `previously(object_grasped)` looks back at t+1 — already `False` — so `object_released`
never fires at all, even though t+2 is exactly the frame release should be detected. A plain
single-frame lookback can't bridge a two-signal gap that spans more than one frame.

Note this is explicitly *not* meant to catch accidental drops — those are supposed to surface as
an `object_grasped_safe` violation instead (see the design-intent discussion below), so the fix
had to close the missed-genuine-release gap without also making accidental drops satisfy
`object_released`.

**Fix:** replaced the single-frame check with a latch, following the same pattern already used
elsewhere in this file for exactly this kind of debounce-spanning gap (`awaiting_settle` /
`settle_watch_object` bridging the release→settle window):

- `pending_release_active` / `pending_release_object`: set the frame `object_grasped` goes
  True→False, naming the object that was grasped (`previous_grasped_object`). Stays latched
  across as many frames as needed. Cleared if `object_grasped` becomes `True` again for *any*
  object (re-grasped before separating, or a stale latch superseded by a new confirmed grasp — not
  a release).
- `object_released := pending_release_active and NOT check_contact(gripper, released_object) and
  gripper_is_opening`, using the released-object identity tracked by the latch, not the current
  `active_object`.
- `check_contact(gripper, object)` here is `_object_gripper_contact_any` — the same *aggregate*
  any-geom contact check that bilateral-contact tightened *grasp* detection away from (item 1
  above). That's the right asymmetry: strict (both fingers) to declare "grasped," but *any*
  remaining contact still counts as "not yet released."
- `settle_watch_object` / `settle_release_object` (feeding property 3) now use the latch's tracked
  identity instead of `previous_active_object`, since by the time release actually fires the
  latch may have been open for several frames and `previous_active_object` could have drifted.

**Design-intent note (confirmed, not changed):** `gripper_is_opening` staying in the formula is
deliberate — an accidental drop (contact lost without the gripper opening) intentionally does
*not* count as `object_released`. It's meant to surface as an `object_grasped_safe` violation
instead: `object_sync` fails (the object accelerates away from the gripper) before or as contact
is fully lost, tripping `object_grasped_safe` while `object_grasped` is still smoothed-`True`
(the two grace windows, `OBJECT_GRASPED_PERSISTENCE_FRAMES` and `GRASP_SAFE_GRACE_FRAMES`, are
both 2 frames, so there's overlap ensuring the violation fires before/as the grasp formally
ends). This is a deliberate separation of concerns between the two LTL properties and was
confirmed as intentional, not a gap, before this fix was scoped.

**General takeaway:** this failure mode — ANDing two signals that have independent,
non-identical debounce/edge timing, using a single-frame `previously(...)` lookback to bridge
them — is generic, not specific to `object_released`. Worth checking other predicates in this
file for the same pattern.

**Reverted (2026-09-01):** the latch was removed and `object_released` restored to the plain
`previously(object_grasped) and NOT object_grasped and gripper_is_opening` check. Reason: the
gap this fix closed was specifically caused by `object_grasped`'s own definition including
`object_sync` (a velocity-based condition — see item 2's revert above), which could fail well
before contact fully cleared, decoupling `object_grasped`'s fall from `check_contact(gripper,
object)` reaching zero by an arbitrary number of frames. Once `object_sync` was removed from
`object_grasped` (item 2), `object_grasped`'s raw signal is driven purely by contact/closed-
finger state — the same underlying joint state `gripper_is_opening` reads — so the two are now
tightly correlated in time and the multi-frame gap the latch existed to bridge is no longer
expected to occur. See `LTL_PREDICATE_TREES.md` cross-cutting item #17 for the note on watching
for this pattern again if either signal ever gains an independently-timed condition.

## 6. `object_released`: added an `object_supported` fallback alongside `gripper_is_opening` (2026-09-01)

**Problem:** `object_released` required `gripper_is_opening`, but a release can also happen
without the fingers ever opening — the arm retracts away from the object while the object stays
resting on a support (e.g. it was already set down, and contact with the gripper breaks purely
because the arm moves off, not because the fingers move).

**Fix:** `object_released := previously(object_grasped) and NOT object_grasped and
(gripper_is_opening or object_supported(released_object))`, where `released_object` is
`previous_grasped_object` (the object that was grasped on the prior frame). `object_supported`
reuses the same helper `object_settled` (Property 3) already uses.

**Why `object_supported` and not `object_stable`:** a plain "is the object moving" check was
considered first, but rejected — a freshly-dropped object can still read as momentarily "stable"
(near-zero velocity) for a frame or two before gravity builds up noticeable speed, which would
have reopened exactly the accidental-drop misclassification this property's design intentionally
avoids (see item 5's design-intent note above). `object_supported` doesn't have that gap: a
falling object is essentially never resting on a surface at the exact frame contact with the
gripper breaks, so it only fires for genuinely at-rest objects.

**Net effect:** `object_released` still never fires for a mid-air accidental drop (neither
`gripper_is_opening` nor `object_supported` holds in that case — it correctly falls through to
an `object_grasped_safe` violation instead), but now also fires for the "retract without
opening, object already resting" case that the `gripper_is_opening`-only version missed.

## 7. `GRIPPER_CLOSED_THRESHOLD`: 0.06 -> 0.035, then 0.04, then 0.0395, then 0.0399 (2026-09-01, revised repeatedly 2026-09-02)

**0.06 -> 0.035:** matched RoboCasa's own default gripper-closed threshold (0.035 is RoboCasa's
default; 0.04 is its documented max). No behavioral rationale beyond aligning with the upstream
default value at the time.

**Reverted to 0.04:** `check_obj_grasped` (`robocasa/utils/object_utils.py`) checks
`gripper_joint1_pos < threshold` (joint2 is always negative in this gripper's convention, so its
half of the check is trivially always true). The Franka Panda finger joint's actual mechanical
travel is `[0.0, 0.04]` (confirmed empirically: max observed joint1 value across a full episode
was 0.04004, at the frame the gripper was commanded fully open). That means the *old* threshold
(0.06) exceeded the joint's physical maximum -- it was unreachable, so the "gripper closed" check
was a **no-op**, always `True` regardless of actual finger position, for as long as it had been
0.06. Tightening it to 0.035 was therefore the first time this check ever became meaningful --
and it happened to land just below a real object's natural propped-open width: holding `bread`
(`ArrangeBreadBasket`) consistently holds the gripper open to ~0.036-0.037 (confirmed via live
sim instrumentation across frames 380-480, one episode), which is `> 0.035` and so failed the
check -- even though bilateral contact was clearly satisfied (4 distinct finger bodies in contact
simultaneously). Net effect: `object_grasped` was `False` for the *entire* bread pick-and-place
portion of that episode (frames ~336-562) -- a total detection blind spot for that whole
grasp-carry-place cycle, not caught by the `sampled`/`v0` runs (both used the old, always-passing
0.06 upstream default before this session's changes, so the joint-position check never actually
excluded anything there either). Reverted to `0.04` (the joint's own physical fully-open limit)
rather than back to 0.06 or forward to some other value -- this is the first threshold that is
both non-trivial (excludes the literal fully-open, nothing-grasped state) and permissive enough to
include any object of any real thickness up to the gripper's max opening, which is definitionally
required for the object to be graspable by this gripper at all.

**Pulled in slightly to `0.0395`:** requested as a small margin below the exact fully-open value
(max observed 0.04004) rather than sitting right at the boundary -- still comfortably above
`bread`'s ~0.036-0.037 in `ArrangeBreadBasket` ep0, so that fix held; just leaves a hair of room
rather than the check's threshold and the joint's own physical limit being (near-)identical.

**Bumped to `0.0399`:** 0.0395 turned out to still be too tight -- `bread` in a *different*
episode (`ArrangeBreadBasket` ep3) props the gripper open even wider than ep0's bread did, to
~0.0395-0.0397 (confirmed via `gripper0_right_finger_joint1`'s raw value, frames 369+), which sits
right at or just above 0.0395 and fails the strict `<` comparison. `object_grasped`/
`raw_grasped_objects` read empty from frame 369 on despite bilateral contact being satisfied fine
(the joint check alone was the blocker). This confirms bread's natural held-width varies
meaningfully episode-to-episode (0.036-0.0397 observed across two episodes so far) and isn't a
single fixed value to build a tight margin around. 0.0399 leaves only ~0.0001 margin below the
observed physical max (0.04004) -- the tightest margin tried, prioritizing not excluding real
objects over keeping headroom below the joint's exact limit. Not yet checked whether any other
object/episode combination needs an even higher value (or whether the joint-position check should
be dropped in favor of trusting bilateral contact alone, once bilateral contact is confirmed --
discussed as an alternative, not implemented).

## 9. Removing persistence frame constants: `CONTACT_PERSISTENCE_FRAMES`, `OBJECT_GRASPED_PERSISTENCE_FRAMES`, `RELATIVE_SPEED_PERSISTENCE_FRAMES`, `GRASP_SAFE_GRACE_FRAMES` (2026-09-01)

**Rationale:** all four were debounce/smoothing buffers introduced to absorb flicker from raw
predicates that were measuring the wrong thing — bilateral contact (item 1), `object_sync`
independence (item 2), and generic single-frame contact-check flicker. With those raw-signal
fixes in place, the structural reason for debouncing was gone; the constants were left at their
existing values (`CONTACT_PERSISTENCE_FRAMES` was already `1`, a no-op) rather than removed,
until this pass.

**What changed, per constant:**

- **`OBJECT_GRASPED_PERSISTENCE_FRAMES`** (was `2`): `object_grasped` now tracks the raw grasp
  candidate directly on both the rising and falling edge — no multi-frame confirmation window.
- **`RELATIVE_SPEED_PERSISTENCE_FRAMES`** (was `2`): `object_sync` now tracks the raw
  relative-velocity check directly — no false-frame grace before flipping.
- **`GRASP_SAFE_GRACE_FRAMES`** (was `2`): `object_grasped_safe` now tracks
  `NOT object_released AND (object_grasped AND object_sync)` directly — no grace window on the
  True→False transition.
- **`CONTACT_PERSISTENCE_FRAMES`** (was `1`, already a no-op numerically): removed the counting
  machinery itself (candidate-tracking dicts, on/off counters) everywhere it appeared, since the
  behavior was already equivalent to the raw check with no debounce. Affected: `forbidden_contact`,
  the initial-contact-pair ignore grace, `robot_contact_raw_active`, `_mark_contaminated`'s gate,
  `robot_contact_clean`, `robot_fixture_contact`, `fixture_obstacle_contact`.

**Code cleanup:** all now-dead counting state was removed too, not just the constants —
`object_grasp_candidate_count`/`object_grasp_missing_count`, `false_counts`/`true_counts` dicts,
`grasp_safe_false_count`, `ignored_initial_contact_pair_missing_counts`,
`robot_contact_raw_candidate_count`, `contamination_transfer_count`, `robot_contact_clean_count`,
`rfc_on_count`/`rfc_off_count`/`rfc_smoothed`, `foc_on_count`/`foc_off_count`/`foc_smoothed` —
including their `monitor_state` init entries and debug-evidence export fields, to avoid leaving
dead/misleading fields in the output.

**Not touched:** `STABLE_PERSISTENCE_FRAME`, `CONTENT_STABLE_PERSISTENCE_FRAMES`,
`MICROWAVE_EMPTY_PERSISTENCE_FRAMES`, `MICROWAVE_OCCUPANCY_PERSISTENCE_FRAMES`,
`SKILL_ONSET_FRAMES`, `PICK_APPROACH_PERSISTENCE_FRAMES`,
`GRASPED_RECEPTACLE_UPRIGHT_GRACE_FRAMES`, and bounded-wait timeouts like
`SETTLE_TIMEOUT_FRAMES` — none of these were diagnosed as papering over a fixed raw-signal bug
this session, so they were left as-is rather than assumed safe to remove.

**Verification:** confirmed `CONTACT_PERSISTENCE_FRAMES` sites were behavior-preserving
simplifications (the constant was already `1`, so `count >= max(1, 1)` was already equivalent to
"raw signal true this frame" before the counting machinery was removed). The other three sites
are genuine behavior changes (previously required 2 consecutive frames), matching the explicit
request to stop debouncing now that the underlying raw signals are trusted.

## 10. `object_released`: OR in `prev(gripper_is_opening)` alongside the current-frame check (2026-09-02)

**Problem:** found via a frame-level spot check of `ArrangeBreadBasket` episode 6 (v1 output,
`monitor/output/CHANGELOG.md`'s v1 entry has the full per-frame table). `gripper_is_opening`
(`predicates.py:572-592`) is a raw single-frame joint-velocity-sign check (mean outward velocity
> 1e-4, no debounce) — it can dip `False` for exactly one frame right at the moment contact breaks
(fingers momentarily near-zero outward velocity), even though it reads `True` on the frame right
before and the frame right after. Since `object_grasped`'s own `True -> False` edge is also a
single frame, that one dip is enough to make `object_released`'s
`prev_object_grasped and not object_grasped and (...)` check miss the release **permanently** —
by the next frame, `prev_object_grasped` is already `False`, so the edge can never be
re-satisfied. Confirmed on `bread` in episode 6: `gripper_is_opening` is `True` at frame 388,
`False` at 389 (the exact frame contact breaks), `True` again at 390; `object_supported` isn't
`True` until 390 either (object not yet settled) — so at frame 389 itself, neither existing
disjunct holds, and `object_released` never fires for this release anywhere in the episode, even
though `object_settled` correctly goes `True` ten frames later.

**Fix:** added `or prev_gripper_is_opening` to `object_released`'s condition (a new
`monitor_state["prev_gripper_is_opening"]`, set from last frame's `gripper_is_opening`, mirroring
the existing `prev_object_grasped` pattern). Additive, not a replacement of the current-frame
check — considered replacing `gripper_is_opening` outright with `prev(gripper_is_opening)`, but
that would drop coverage of the ordinary case where opening and contact-loss land on the *same*
frame with no ramp-up, which is the common case, not the exception.

A separate case in the same episode (frame 445, `basket`) was also examined and judged **not** a
bug worth fixing — `object_supported`'s fallback firing on an incidental fixture contact during
transport was judged an acceptable true positive, not a false one, so no stability check was
added there.

**Not yet re-extracted:** this landed after the v1 SLURM extraction run had already started, so
`monitor/output/v1_2026-09-01_bilateral_contact_and_settle_fixes/` does **not** reflect this fix —
it will need a new `v2_.../` directory once re-run.

## 11. `object_sync`: lever-arm-corrected linear velocity comparison (2026-09-02)

**Problem:** flagged as a pre-existing (not introduced this session) bug in `OBVIOUS_ISSUES.md`
and the v1 `CHANGELOG.md` entry: `_object_eef_relative_speeds` compared the object's raw linear
velocity directly against the eef's raw linear velocity. For a rigid grasp with the object's
reference point offset from the eef site, rotating the whole assembly (e.g. turning to walk to a
counter) makes these two velocities differ by `ω × r` even with zero actual slip — a real physics
effect, not sensor noise, so no threshold tuning could fix it without also hiding genuine slip.
Confirmed on `ArrangeBreadBasket` ep0: at frame 570, `basket` vs. eef angular velocity matched
almost exactly (rigidly attached), but raw linear velocity differed by ~0.12 m/s (over
`OBJ_LINEAR_STABLE_THRESHOLD`), causing `object_grasped_safe` to read `False` for 259 straight
frames (566 to episode end) despite no real safety issue.

**Fix:** compute the rotation-corrected expected object velocity —
`v_expected = v_eef + ω × (pos_object - pos_eef)`, using `eef_ang_vel` as `ω` (the driving link;
already shown to closely track the object's own angular velocity for a rigid grasp) — and compare
the object's actual velocity against `v_expected` instead of against `v_eef` directly. Falls back
to the old uncorrected comparison if position data for either point is unavailable. Verified
directly against the motivating case: frames 568-579 of ep0 drop from a raw residual of
~0.04-0.12 m/s (over threshold) to a corrected residual of ~0.002-0.05 m/s (under threshold, except
one still-real transient at 566-567 where angular velocities hadn't yet aligned either).

## 12. `object_sync`: prefer actual contact-point slip speed over the CoM-based lever-arm correction (2026-09-02)

**Problem:** item 11's lever-arm correction assumes the object's whole body is rigidly locked to
the eef site and compares velocities at two reference points (object CoM / pose origin, eef site)
that generally aren't the actual touching surface. That holds for a perfectly rigid grasp, but
isn't the physically correct thing to check in general -- e.g. contents shifting inside a held
container, or any compliance in the grasp, would show up as a spurious residual at the CoM/site
even with zero actual slip at the fingers.

**Fix:** added `_object_contact_slip_speed(name)`, which finds the actual gripper/object contact
point(s) from `env.sim.data.contact[i].pos` (reusing the same contact-scanning loop as
`_object_gripper_bilateral_contact`), computes each body's material-point velocity *at that exact
position* (`v = linear_vel + angular_vel × (contact_pos - reference_pos)` for each of object and
gripper), and compares those -- the direct no-slip condition at the finger/object interface, not
an approximation via CoM/site reference points. `_object_eef_relative_speeds` now prefers this
whenever there's active contact, falling back to item 11's lever-arm-corrected CoM comparison only
when there's no contact data available that frame (e.g. right as contact breaks). Not yet verified
against real data at time of writing (unlike items 1/3/4/11, this can't be checked against
already-recorded `privileged_information_N.json` dumps -- contact positions are live sim state,
not saved to the JSON -- verification is the pending v2 re-run).

## 13. `object_sync`: position-based accumulated slip instead of instantaneous velocity (2026-09-02)

**Problem:** items 11/12 fixed the *measurement* of relative velocity, but even a correctly
measured velocity-based check has an inherent limitation: real, brief angular-velocity transients
during ordinary carrying (turning a corner, accelerating/decelerating) reached up to ~1.1 rad/s in
episodes that otherwise looked completely safe on video (`ArrangeBreadBasket` ep0 frame 640, ep3
frames 783-799 -- see `monitor/output/CHANGELOG.md`'s v1/v2 entries and the frame-level data
gathered while investigating this). No static velocity threshold can separate "brief real wobble,
no net slip" from "actually unsafe" -- raising the threshold to tolerate the wobble also hides
real slip; keeping it tight flags normal motion.

**Fix:** replaced the instantaneous-velocity comparison with an accumulated-*position* comparison.
At grasp onset (the same edge `source_support_fixtures`/`source_support_objects` are captured at),
record the object's position and orientation relative to the eef, in the eef's own frame (a
one-time baseline, `monitor_state["grasp_slip_rel_offset"]`/`["grasp_slip_rel_quat"]`). Every frame
after, compute where the object *should* be if it had moved perfectly rigidly with the eef since
that instant (`v_expected = eef_pos + eef_quat * rel_offset`, likewise for orientation via
quaternion composition), and compare to the actual pose -- the residual is the accumulated slip.
A momentary wobble that returns to the same relative pose nets to ~0 drift; a genuine progressive
slip accumulates and stays large. New helper `_object_grasp_slip(name)`; new quaternion helpers
`_quat_conjugate`/`_quat_multiply`/`_quat_rotate_vector`/`_quat_angle`; new orientation getters
`_object_orientation`/`_eef_orientation`. `_object_sync` now calls this first, falling back to the
old velocity-based `_object_eef_relative_speeds` only if no baseline is available (e.g. right after
a monitor restart mid-grasp, before any onset edge could fire).

**New constants:** `GRASP_SLIP_LINEAR_THRESHOLD = 0.03`, `GRASP_SLIP_ANGULAR_THRESHOLD = 0.3` --
not yet validated against real data at time of writing (unlike most other constants in this file);
starting points pending the `v3` extraction run.

**Not removed:** `_object_eef_relative_speeds`/`_object_contact_slip_speed` (items 11/12) are kept
as the fallback path, not deleted -- they're correct measurements of a real (if not always useful)
quantity, and still needed for the no-baseline case.

## 14. Fixed a quaternion component-order bug in `_object_orientation`/`_eef_orientation` (2026-09-02)

**Problem:** found while spot-checking item 13 on real data -- `ArrangeBreadBasket` ep0 showed
`basket` apparently rotating ~2.88 rad (~165 degrees) relative to the eef over frames 564-791, and
`bread` rotating ~0.87 rad (~50 degrees) over frames 362-486, in an episode where the user directly
observed no such rotation on video for bread. Diagnosed by checking whether the object's and eef's
own *absolute* (world-frame) rotation axes over the same window pointed the same way (they should,
for a rigidly-attached object) -- they didn't: dot product of the two axes was consistently
strongly *negative* (~-0.82 to -0.97) for both bread and basket, an anti-parallel pattern
inconsistent with rigid attachment but consistent with a systematic sign/order bug affecting both
object types identically. Root cause: `kitchen_ext.py`'s `_pose_from_body_id` (objects) and
`_pose_from_site_id` (eef) both store `"orientation"` in **xyzw** order
(`T.convert_quat(..., to="xyzw")`, and `Rotation.as_quat()` which defaults to xyzw) --
`_object_orientation`/`_eef_orientation` were reading `quat[0]` as the scalar/w component, when
it's actually `quat[3]`.

**Fix:** added `_xyzw_to_wxyz(quat_xyzw)`, applied in both `_object_orientation` and
`_eef_orientation` before returning. Re-verified on the same real data after the fix: the
object/eef absolute-rotation-axis dot product flipped to ~+0.996 to +0.997 (correctly parallel),
bread's relative rotation dropped to ~0.036 rad (~2 degrees, matching the "no visible rotation"
observation), and basket's dropped to ~0.34-0.35 rad (~19-20 degrees) -- real, but an order of
magnitude smaller than the buggy value, and no longer growing without bound.

## 15. `object_sync`/`_object_grasp_slip`: frame-to-frame drift instead of accumulated-since-onset (2026-09-02)

**Problem:** item 13's accumulated-since-onset design has its own failure mode, distinct from the
quaternion bug above: if the object slips once (a real, one-time settling shift right after being
lifted, say) and then stays put at the new relative pose, the residual `obj_pos - expected_pos`
becomes a **fixed, non-decaying offset** for the rest of the grasp, since `expected_pos` is still
anchored to the original onset baseline forever. If that one-time shift is larger than the
threshold, every subsequent frame gets flagged as unsafe even though nothing is still slipping --
the object already stabilized.

**Fix:** `_object_grasp_slip` now overwrites `monitor_state["grasp_slip_rel_offset"]`/
`["grasp_slip_rel_quat"]` to *this* frame's actual relative pose at the end of every call,
regardless of whether slip exceeded threshold. The comparison is now against the immediately
preceding frame's relative pose, not the original grasp-onset pose -- a one-time shift is flagged
once (correctly) and stops being flagged the moment the object reaches a new stable relative pose;
a genuinely continuous slip keeps producing frame-to-frame drift and keeps getting flagged.

**Trade-off, confirmed on real data (not a full fix, a different set of trade-offs):** re-ran
`ArrangeBreadBasket` ep0 with this change -- 0/19 violated (previously 1/19, `rc_grasp_remains_
safe_until_release` at frame 641 with the accumulated-since-onset + quaternion-fixed version).
Checked why: the basket's real ~19-20 degree swing (item 14) spreads across ~150 frames at
`call_stride=16`, and the actual per-frame deltas measured directly are tiny -- mean 0.0053 rad
(~0.3 degrees), max 0.059 rad (~3.4 degrees), both far under `GRASP_SLIP_ANGULAR_THRESHOLD` (0.3)
at every single frame. A per-frame check is, at this temporal resolution, close to a coarse
average-velocity check again -- immune to the item 13 problem (stale baseline) and the original
velocity-based over-sensitivity to brief transients, but now blind to slow, continuous drift that
never spikes in any one frame yet accumulates to something real over many frames. None of the
three approaches tried this session (instantaneous velocity / accumulated-since-onset /
frame-to-frame) satisfies all three properties (immune to brief transients, forgets one-time
settles, still catches slow continuous drift) simultaneously -- flagged as an open design question,
not resolved. A bounded-recent-window accumulation (neither "forever since onset" nor "just one
frame") was discussed as a possible middle ground but not implemented.

## 16. `object_released`: require `_object_stable_relative` in the `object_supported` fallback (2026-09-02)

**Problem:** the `object_supported` fallback branch (item 6) fires on any contact with a support
surface, with no requirement that the object actually be at rest. Confirmed false positives:
`ArrangeBreadBasket` ep6 frame 445 (basket still moving 0.1-0.3 m/s, a one-frame bilateral-contact
dropout mid-transport happened to graze a fixture) and `ArrangeTea` ep0 frame 85 (`obj2` still
actively held, same one-frame-dropout pattern, `object_supported` already `True` throughout).
The `ArrangeTea` case cascaded into a second false violation: the phantom release at frame 85/92
never settled, tripping `rc_released_object_eventually_settles`'s timeout ~96 frames later.

**Fix:** added `and _object_stable_relative(previous_grasped_object)` to that branch. Consistent
with the branch's own original intent (a deliberately placed-down object should already be at rest
by the time the gripper retracts) -- not a narrowing of scope, just closing a gap the original
condition left open. Doesn't reopen the accidental-drop exclusion either: a freshly-dropped object
is still in free-fall at the exact frame contact breaks, so `_object_stable_relative` reads
`False` there too.

**Verified, with a caveat:** `ArrangeTea` ep0's false `rc_released_object_eventually_settles` is
gone. But the same underlying one-frame bilateral-contact dropout (`object_grasped` itself
flickers `False` for exactly one frame, frame 85, while the object is clearly still being held)
now surfaces as a *different* violation instead: `rc_grasp_remains_safe_until_release`, since
`G(object_grasped -> object_grasped_safe U object_released)` sees a frame where neither the
obligation (`object_grasped_safe`, which requires `object_grasped=True`) nor the resolve
(`object_released`, now correctly `False`) holds. This fix didn't eliminate the false positive --
it moved it from one property to another. The actual root cause is the one-frame flicker in
`_object_gripper_bilateral_contact`/`_object_is_grasped` itself (item 1 was meant to eliminate
exactly this kind of flicker via the bilateral-contact requirement, and mostly does, but not in
every case) -- fixing that at the source, rather than patching each downstream property
individually, is the real follow-up, not yet done. Accepted as a net improvement for now (one
concrete symptom addressed, the underlying cause documented and tracked rather than hidden).
