# Changelog — 2026-09-02: grasp-safety LTL split, `object_left_gripper`, viewer occurrence-breakdown fixes

Context: `rc_grasp_remains_safe_until_release`'s single formula conflated two different
questions ("does the grasp stay synced while held" and "was the eventual release a real
release, not an accidental drop") into one `until`, which meant a bilateral-contact detection
flicker (a real, one-frame artifact — see `BILATERAL_CONTACT_FLICKER_BUG.md`) could poison the
whole property for the rest of the episode even when the object was never actually let go. This
log covers splitting that property in two, and the multi-round iteration needed to get the new
property's "was this drop actually a release" formula right without introducing new bugs along
the way — plus the viewer-side fixes needed to make the breakdown display match what the
formula actually does.

All predicate/spec changes are scoped to `SafeManip/monitor/` (predicates, specs, the repeated-
violation monitor) — the upstream `robocasa/` package was not touched. Viewer changes are
scoped to `SafeManip/viewer/`.

## 1. New predicate: `object_dropped`

`predicates.py`: `object_dropped = _bool(prev_object_grasped and not object_grasped)` — the raw
grasp-ended edge, true for exactly one frame whenever `object_grasped` goes True → False, for
*any* reason (a clean release, a silent drop, or a one-frame bilateral-contact flicker).
Exported so the two new properties below can each resolve their own "until"/"instant" on this
alone, instead of sharing one formula that conflates them.

## 2. Split `rc_grasp_remains_safe_until_release` into two properties

- **`rc_grasp_remains_synced_until_dropped`**: `G(object_grasped -> (object_sync U
  object_dropped))` — recovery: `G(object_grasped & !object_sync -> F(object_sync |
  object_dropped))`. Unchanged since first written this session; no known issues.
- **`rc_dropped_object_was_released`**: whenever a grasp ends, that must be an actual release
  (gripper-opening/settled evidence), not an accidental loss of grasp. Its formula went through
  4 rounds (below) before landing on a version verified correct against all of
  `ArrangeBreadBasket` episodes 0, 1, 4, 6, 7.

`repeated_violation_monitor.py`: `build_repeated_grasp_monitor` replaced with
`build_repeated_grasp_sync_monitor` + `build_repeated_object_drop_release_monitor`.
`monitor_metrics.py`'s `"grasp_damage_safety"` category updated to list both new properties.

## 3. Critical architectural discovery: `specs.py`'s `"ltl"` field is live, not documentation

`symbolic_properties.py`'s `_materialize_property()` compiles a real `LTLfDFA` directly from
`spec["ltl"]`, and `RoboCasaSymbolicMonitor.step()` uses that DFA's accepting/trap status to
build the `history` that the *primary* violated/satisfied classification in
`run_monitor_on_privileged.py` is based on. This is completely independent of
`repeated_violation_monitor.py`'s own `main_ltl`, which only feeds the *secondary*
`repeated_violation_episodes` detail (duration/recovered stats), not the primary call at all.

A first attempt at `rc_dropped_object_was_released` left `specs.py`'s `"ltl"` field as the old,
simpler `"G(object_dropped -> object_released)"` string (to keep `spec_derive.py`'s regex-based
viewer shape-parser happy) while writing the "real" formula only into
`repeated_violation_monitor.py`. That silently kept the *primary* classification on the stale,
flicker-sensitive formula the whole time, independent of every subsequent round below — caught
via a direct isolated `LTLfDFA` test against a real flicker trace returning the correct
(accepting) result while the actual pipeline still reported it violated. Fixed by always keeping
`specs.py`'s `"ltl"` field and `repeated_violation_monitor.py`'s `main_ltl` textually identical
(there is no automatic check enforcing this — a real footgun, noted inline at both sites).

## 4. Round 1: `F(object_grasped)` escape — cross-object misattribution bug

**Formula:** `G(object_dropped -> (object_released | F(object_grasped)))` — "a drop immediately
followed by a regrasp never counts as a violation."

**Bug:** `object_grasped` is a global, object-identity-less boolean (true whenever *anything*
active object is grasped) — no per-object tagging in the evaluation model. Confirmed on
`ArrangeBreadBasket` ep1: `bread` dropped at frame 443 with no release evidence, never
regrasped — but `F(object_grasped)` was satisfied by an unrelated *later* grasp of `basket`
(confirmed via `active_object` role-set: bread through frame ~510, basket from ~515 onward),
producing a false negative (falsely "satisfied" instead of correctly "violated").

## 5. Round 2: `!(object_stable_relative & object_supported) U object_grasped` — fixes round 1, introduces a new false positive

**Formula:** `G(object_dropped -> (object_released | (!(object_stable_relative &
object_supported) U object_grasped)))`.

**Why it fixes round 1 without a dedicated identity-tracking predicate:** `active_object`
doesn't switch away from the just-dropped object until the robot moves on to touch/grasp
something else, and a genuinely-dropped object settles (`stable_relative & supported` becomes
true) *before* that switch happens if nothing regrasps it first — so the until stays correctly
scoped to the same object via timing alone. Verified: ep1 (real drop) correctly violated, ep4
(regrasped before ever settling) correctly satisfied.

**New bug:** `object_stable_relative`/`object_supported` are exported without the debounce
`object_stable` already gets via `_persistent_bool`/`STABLE_PERSISTENCE_FRAME` (see
`KNOWN_BUGS.md` #10 for the general pattern). A single noisy frame of
`stable_relative & supported = True` can incorrectly break the until early. Confirmed on ep7's
second drop event (`basket` @716, a fast open-then-reclose recatch, regrasped @718): frame 717
shows one solitary `stable_relative & supported = True` frame sandwiched in between — wrongly
flagged as violated, when physically nothing ever came to rest (compare to a genuine settle
elsewhere in the same episode holding continuously true for 30+ frames).

## 6. Round 3: `object_left_gripper` (raw mesh contact) — fixes round 2's bug, has the same problem in a new place

New predicate, first version: `object_left_gripper = not _object_gripper_contact_any(obj_name)`
— true once the object's mesh is no longer in contact with any gripper geom at all. Formula:
`G(object_dropped -> (object_released | (!object_left_gripper U object_grasped)))`, recovery:
`G((object_dropped & !object_released) -> F(object_grasped | object_left_gripper))`.

Fixed ep7's frame-717 false positive (contact, unlike stable/supported, doesn't care whether the
object has come to rest — it stays "not left" throughout a fast recatch). But confirmed via
direct MuJoCo contact-solver inspection (loaded the real sim state at ep7 frame 716) that raw
contact is *also* not noise-free: at frame 716 itself (the trigger frame), MuJoCo reports zero
active gripper-basket contact pairs among all 66 contacts that frame — a one-frame
contact-solver flicker, same class of noise as every other contact-based signal in this file,
just relocated to a new atom. `until` requires `!object_left_gripper` to hold starting at the
trigger frame itself, so this one-frame flicker broke it immediately.

## 7. Round 4 (final): AABB-overlap-based `object_left_gripper`

Per discussion: treating raw contact as equivalent to "the object's original shape overlapping
the gripper's original shape" is too brittle (contact solver resolution is inherently binary
and margin-dependent); redefined using axis-aligned bounding box (AABB) overlap instead — the
gripper as one rectangular region spanning its jaws (including the open space between the two
fingers, which a bare contact check has no notion of), checked against whether the object's
own AABB overlaps it at all. AABB overlap depends on continuous position, not a binary
contact-solver resolution, so it changes smoothly instead of flickering at the contact-margin
boundary.

```python
_gripper_aabb_now = _gripper_aabb()
_object_aabb_now = _object_contact_aabb(str(obj_name)) if has_active_object else None
_gripper_object_overlap = (
    _gripper_aabb_now is not None
    and _object_aabb_now is not None
    and _aabb_intersects(_gripper_aabb_now, _object_aabb_now)
)
object_left_gripper = _bool(has_active_object and not _gripper_object_overlap)
```

Reuses existing shared helpers throughout (no new geometry code): `_gripper_aabb()` (same
source `_gripper_far_from_object`/`_pick_swept_endpoint_aabbs`/`_gripper_object_distances`/
`_gripper_inside_fixture_interior` already use) and `_aabb_intersects()` (same overlap test the
region-blocker family already uses).

**Bug found while implementing this (see `KNOWN_BUGS.md` #11 for full detail):** deliberately
does *not* use the general `_object_aabb(obj_name)` helper — its first-choice source,
`_object_ou_bbox_aabb()` (`env.objects[name].get_bbox_points()`), returns a bounding box for
`basket` that's ~0.1m below its actual held position *continuously* while it's being carried
(confirmed via direct frame-by-frame debugging: `_object_position("basket")` Z ≈ 0.92 vs.
`_eef_position()` Z ≈ 1.04, and `_object_ou_bbox_aabb`'s own Z-range never overlapping the
gripper's Z-range at all during an actual, confirmed grasp). Using `_object_aabb()` as originally
planned would have made `object_left_gripper` read `True` (wrongly "left") continuously through
an entire real grasp — a much worse bug than the one-frame flicker this predicate exists to fix.
Used `_object_contact_aabb()` (one of `_object_aabb`'s own fallback options, built from the
object's current contact-geom positions the same way `_gripper_contact_aabb()` builds the
gripper's) directly instead, bypassing the buggy first choice. This is not fixed at the shared
`_object_aabb()`/`_object_ou_bbox_aabb()` level — other callers of `_object_aabb()` still go
through the buggy path and haven't been re-checked; see `KNOWN_BUGS.md` #11 for the ~25 call
sites potentially affected.

**Verified** against `ArrangeBreadBasket` episodes 0, 1, 4, 6, 7 (all re-extracted with the
current predicate set and re-run through the full monitor pipeline):

| episode | case | result |
|---|---|---|
| 0 | bread/basket clean releases | satisfied ✓ |
| 1 | bread: real drop, never regrasped | **violated** ✓ |
| 4 | bread: regrasped before ever settling | satisfied ✓ |
| 6 | basket: 1-frame flicker, immediate regrasp | satisfied ✓ |
| 7 | bread: clean release; basket: fast recatch (was round-2/3's false positive) | satisfied ✓ |

Final formula:
```
main_ltl:     G(object_dropped -> (object_released | (!object_left_gripper U object_grasped)))
recovery_ltl: G((object_dropped & !object_released) -> F(object_grasped | object_left_gripper))
```

## 8. Viewer: occurrence-breakdown fixes for the new compound LTL shape

`spec_derive.py`: added two new regexes (the existing 3 shapes — invariant/until/instant — don't
cover this): `_INSTANT_WITH_ESCAPE_RE` for `G(trigger -> (check | F(escape)))` (round 1's shape,
kept for reference) and `_INSTANT_WITH_UNTIL_ESCAPE_RE` for `G(trigger -> (check |
(!guard_expr U escape)))` (rounds 2-4's shape) — the latter also captures the guard expression's
individual atom(s) (`escape_guard_atoms`), needed by the fix below.

`server.py`'s `compute_occurrences` (`pattern == "instant"` branch) originally only checked
whether `check` was true at the same frame as `trigger` — it had no notion of the escape/until
at all, so every occurrence (a genuine unresolved violation and a harmless recatch alike) looked
identical in the breakdown table. Fixed by actually simulating the until forward from the
trigger frame against the real traces: resolves if `escape` fires before `guard_atoms` are ever
all simultaneously true; fails (a real, unresolved violation) if `guard_atoms` go all-true first.
Two follow-on fixes to this:

- **`violated_frames` must stay empty when the until resolves.** Per real LTLf semantics, if
  the until resolves, the whole `trigger -> (check | until)` implication is actually *true* at
  the trigger frame given how the rest of the trace plays out — even though `check` itself read
  false right there. An earlier version of this fix still listed the trigger frame in
  `violated_frames`, which made the timeline mark it red even though nothing was ever really
  violated (confirmed on ep1: `basket`'s harmless @523 flicker was shown identically to
  `bread`'s real, unresolved @443 violation until this was corrected).
- **Timeline window was cropping out the eventual resolution.** The visible window is sized as
  `[min(marks) - 5, max(marks) + 15]`. For an occurrence that resolves via the until (not an
  instant same-frame check), `guard_atoms` can take a while longer than 15 frames past the last
  mark to actually flip true on their own (e.g. the gripper genuinely separates from the object
  well after the property itself already resolved) — without accounting for that, the window
  never showed it, making it look like `object_left_gripper` "never becomes true," when it does,
  just outside the rendered range (confirmed on ep7: last mark @926, window cropped to 941,
  actual separation @942; ep0: last mark @791, window cropped to 806, actual separation @806 —
  right at the boundary, effectively invisible). Fixed by adding an `eventual_separation` tracker
  to both resolution paths (instant-check-passed and resolved-via-until) that scans forward from
  the resolution frame for the first frame where `guard_atoms` are all true, and including it in
  the window-sizing calculation.

## 9. Viewer: `escape`/`escape_guard_atoms` weren't marked "covered," causing duplicate predicate rows

`server.py`'s `extra_top` auto-derivation (the "whatever's left over after
trigger/obligation/resolve/guard/check and their own children" logic) only checked those 5
role names when computing what's already "covered" by a top-level row — it didn't know about
the newer `escape`/`escape_guard_atoms` fields (added in section 8 above for the
instant-with-until-escape shape). Since `object_grasped` (`rc_dropped_object_was_released`'s
`escape`) and `object_left_gripper` (its `escape_guard_atoms`) are both already top-level LTL
atoms (picked up directly from the `ltl` string by `extract_ltl_atoms()`, same as `trigger`/
`check`), they weren't excluded from `extra_top` and ended up rendered as a *second*, duplicate
row each in the viewer's predicate breakdown. Fixed by adding `escape`/`escape_guard_atoms` to
the `_covered` set alongside the other 5 roles.
