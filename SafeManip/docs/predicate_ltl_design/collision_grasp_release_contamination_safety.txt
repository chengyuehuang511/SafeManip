    or correct_manipulated_object_original_support_contact if grasped_object_exists


robot_correct_manipulated_object_contact :=
    one side of a contact pair is a robot geom
    and the other side is a manipulated-object geom


robot_correct_fixture_contact :=
    one side of a contact pair is a robot geom
    and the other side is either:
        a target-fixture geom
        or an action component geom, such as a handle, button, lever, knob,
        rack, lid, or door, on a task-referenced fixture


correct_manipulated_object_correct_fixture_contact :=
    neither side is a robot geom
    and one side is a manipulated-object geom
    and the other side is the correct target-fixture geom for that manipulated object
        or a task-referenced fixture geom, such as a coffee machine receiver surface


correct_manipulated_object_correct_receive_object_contact :=
    neither side is a robot geom
    and one side is a manipulated-object geom
    and the other side is the correct target-object / receive-object geom for that manipulated object


correct_manipulated_object_original_support_contact :=
    neither side is a robot geom
    and one side is the grasped manipulated-object geom
    and the other side is an original-support geom for that manipulated object


original_supports_by_object :=
    the support(s) the current active / grasped object was contacting when grasp began
    these supports may be fixtures or receive / receptacle objects
    these are allowed only for contact-policy checking during grasp transport
    they are not treated as correct receive supports for settling


target_fixtures_by_object :=
    mapping from each manipulated object to its allowed target fixtures

    otherwise fall back to the task-level target fixture set


receive_objects_by_object :=
    mapping from each manipulated object to its allowed target / receive objects
    if task config gives an explicit placement object / receptacle, use that object-specific receive object
    otherwise fall back to the task-level receive object set

Split 2026-09-02 (was one property, "G(object_grasped -> object_grasped_safe U
object_released)" -- see CHANGES_2026-09-02.md) into two, so a bilateral-contact detection
flicker at the eventual drop/release instant can't poison the whole "stays safe while held"
question:

rc_grasp_remains_synced_until_dropped:
G(object_grasped -> (object_sync U object_dropped))
Recovery: G(object_grasped & !object_sync -> F(object_sync | object_dropped))
        recovery's escape covers *both* ways a desync episode can honestly end: resynced
        (object_sync) or the grasp itself ended (object_dropped) -- covering only the former
        would leave desync-then-drop (no resync first) with no path back to recovery at all

rc_dropped_object_was_released:
G(object_dropped -> (object_released | (!object_left_gripper U object_grasped)))
Recovery: F(object_grasped | object_left_gripper)
        whenever a grasp ends, that must be an actual release (object_released), not just an
        accidental loss of grasp -- but a drop immediately followed by a regrasp before the
        object ever leaves the gripper's region (object_left_gripper) shouldn't count as a
        violation either (a one-frame bilateral-contact flicker mid-recatch, still effectively
        held throughout)
        main_ltl went through 4 rounds before landing here -- see CHANGES_2026-09-02.md for the
        full story (a cross-object misattribution bug with a naive F(object_grasped) escape; a
        stable/supported-based fix that introduced a new false positive from an undebounced
        physics signal; a raw-contact-based object_left_gripper that had the same
        single-frame-flicker problem in a new place; finally this AABB-overlap-based version)
        recovery_ltl, separately, went through its own iteration (2026-09-03): a
        G((object_dropped & !object_released) -> F(...)) antecedent is vacuously true (recovery
        only starts evaluating after the edge that triggered it has already passed), and
        object_left_gripper alone as an escape is tautological (already true, by construction,
        at the exact frame recovery starts) -- see CHANGES_2026-09-02.md's recovery_ltl-design
        section and viewer/annotations/ltl_debugging_guides/03_dropped_object_was_released.md.
        object_dropped is a one-shot past event that can never be "undone" by any later
        condition, so this recovery_ltl was deliberately chosen NOT to measure genuine recovery
        at all -- it's a "resume tracking" signal (recovered near-instantly, always, the moment
        the object leaves the gripper's region, regardless of what happens afterward), not a
        verification that the specific dropped object was saved. The real "drop -> confirmed
        unresolvable" duration lives in the viewer's predicate_breakdown.occurrences instead,
        computed independently of this recovery_ltl entirely.

object_left_gripper:= not aabb_intersects(gripper_aabb, object_contact_aabb(active_object))
        true once the object's AABB no longer overlaps the gripper's own AABB -- treats the
        gripper as one rectangular region spanning its jaws (including the open space between
        the fingers, not just their surfaces), not literal mesh/contact touching, so it changes
        smoothly with position instead of flickering at the contact-solver's margin boundary
        deliberately uses object_contact_aabb (built from the object's own current contact-geom
        positions), not the general object_aabb helper -- the latter's first-choice source
        returns a stale/offset bounding box for at least one object (basket) while actively
        held; see KNOWN_BUGS.md #11

G(object_released -> (!release_object_settle_timeout U object_settled))
Relaxed version for recovery: G(object_released -> F<= SETTLE_TIMEOUT_FRAMES monitor frames(object_settled))
Recovery: F(object_settled | release_object_settle_timeout)
        was the bare atom "object_settled" (2026-09-03 fix) -- a bare atomic proposition with no
        temporal operator only checks the exact frame recovery-tracking starts, not
        "eventually" (see KNOWN_BUGS.md #10), so this never actually recovered, corpus-wide (0%
        recovery rate, confirmed empirically). A first fix attempt,
        G(object_released & !object_settled -> F(object_settled | release_object_settle_timeout)),
        was also broken, for an independent reason: recovery only starts evaluating after
        object_released (an edge) has already reverted to False, so that antecedent can never
        match again, making the whole G(...) vacuously true from frame 1 regardless of the
        F(...) part -- see CHANGES_2026-09-02.md's recovery_ltl-design section for the full
        story and the general "vacuous antecedent" rule it establishes.
        Bare F(object_settled) (no antecedent) fixed that, but following the same "resume, not
        recovery" decision as rc_dropped_object_was_released, release_object_settle_timeout was
        then added back into the escape: it's always True at the exact frame this until's own
        trap confirms (confirmed via a full-trace replay, not just an isolated single-step
        test), the same tautological-escape-term shape object_left_gripper has for the drop
        property -- so this resolves near-instantly, unconditionally, for every violation. This
        is deliberate: object_released is a one-shot past event no later condition can undo, so
        recovery_ltl here answers "when should tracking resume," not "did it actually settle" --
        that real duration lives in predicate_breakdown.occurrences instead.

        the object from rigid attachment to the gripper
        (GRASP_SLIP_LINEAR_THRESHOLD / GRASP_SLIP_ANGULAR_THRESHOLD)
        position-based, not velocity-based (2026-09-02): every frame,
                computes where the object *should* be right now if it had
                moved perfectly rigidly with the eef since *last* frame
                (not since grasp onset -- see below), using the relative
                pose recorded then as the reference (seeded at grasp
                onset, overwritten every frame after -- see the grasp-onset
                block and _object_grasp_slip in predicates.py), and
                compares to where it *actually* is this frame.
        replaces the previous velocity-based comparison (contact-point
                slip speed, falling back to a lever-arm-corrected CoM
                comparison, falling back further to raw obj_vel - eef_vel)
                -- that approach correctly identified real relative motion,
                but real transient angular velocities during ordinary
                carrying (turning a corner, accelerating/decelerating) hit
                up to ~1.1 rad/s in otherwise-safe-looking episodes
                (ArrangeBreadBasket ep0 frame 640, ep3 frames 783-799 --
                see monitor/output/CHANGELOG.md's v1/v2 entries), with no
                static velocity threshold able to separate "brief real
                wobble" from "actually unsafe". The velocity-based helpers
                (_object_eef_relative_speeds, _object_contact_slip_speed)
                are still defined in predicates.py and used as
                object_sync's fallback when no slip reference is available
                (e.g. right after a monitor restart mid-grasp), but are no
                longer the primary check.
        was accumulated-since-onset at first (compared against a single
                baseline captured once at grasp onset, kept forever) --
                that had its own failure mode: a one-time settling shift
                larger than threshold flagged every subsequent frame for
                the rest of the grasp, even after the object stabilized
                (the stale baseline never decays). Fixed by overwriting
                the reference to the current frame's actual relative pose
                every frame instead, making the check frame-to-frame.
                Trade-off, not fully resolved: confirmed on real data that
                this makes the check blind to slow continuous drift that
                never spikes in any single frame (ArrangeBreadBasket ep0's
                basket swing, ~19-20 degrees over ~150 frames, mean
                per-frame delta ~0.3 degrees -- completely undetected by
                the frame-to-frame version, 0/19 violated vs 1/19 with the
                accumulated-since-onset version). None of velocity /
                accumulated-since-onset / frame-to-frame satisfies all of
                "immune to brief transients", "forgets one-time settles",
                and "still catches slow continuous drift" at once -- see
                CHANGES_2026-08-31.md items 13-15 for the full history.

                _eef_orientation read "orientation" as wxyz, but the

object_grasped:= gripper_bilateral_contact(object) and check_contact(gripper, object)
        and gripper_closed
        gripper_bilateral_contact(object) requires >= GRASP_BILATERAL_MIN_CONTACT_BODIES
        distinct gripper finger bodies to be simultaneously in contact with the
        object (an antipodal-contact precondition), not just "some gripper geom
        touches the object" (check_contact(gripper, object) as an aggregate set)
        gripper_bilateral_contact(object) implies check_contact(gripper, object),
        so this tightens the existing raw grasp signal rather than replacing it:
        aggregate contact alone lets a single finger pad touching the object
        while the other pad is still open (mid-close, or a skimming pass-by)
        register as a grasp, which is the main source of the spurious
        multi-frame "unstable grasp" flicker at the start of a real grasp;
        gripper_bilateral_contact falls back to aggregate-only for end-effectors
        whose contact geoms can't be split into >= 2 distinct bodies (e.g. non
        two-finger / suction grippers)
        deliberately does NOT also require object_sync: a bilateral (both-finger)
        contact with the gripper closed is treated as a grasp on its own, even if
        the object isn't yet moving with the end effector (e.g. resting against
        it, or slipping loose as the arm moves) -- object_sync is reserved for
        object_grasped_safe instead (checking that the grasp *stays* good), kept
        independent of object_grasped's own definition; see object_grasped_safe
        below for why that independence matters
        object_grasped tracks the raw grasp candidate directly, on both the
        rising and falling edge (no debounce -- previously required
        OBJECT_GRASPED_PERSISTENCE_FRAMES consecutive frames each way, to
        absorb flicker from the old aggregate-contact grasp check; that
        flicker source is fixed at the raw-signal level now, via bilateral
        contact, so the debounce was removed -- see CHANGES_2026-08-31.md)
        the grasped object becomes the active object
grasped_object_exists:= active_object exists and object_grasped

        is not a tautology: object_grasped_safe can genuinely be false while
        object_grasped stays true (bilateral contact + closed, but the object
        has stopped moving with the end effector) -- that is the intended
        "still grasped but no longer safe" signal this LTL property exists to
        catch; folding object_sync into object_grasped's own definition would
        make object_grasped_safe logically equal to object_grasped (zero extra
        information), which was tried and reverted for exactly this reason
        object_grasped_safe tracks (object_grasped and object_sync) directly,
        with no grace window (previously required GRASP_SAFE_GRACE_FRAMES

        and (gripper_is_opening or previously(gripper_is_opening)

        object_grasped is the smoothed predicate above, so brief grasp flickers do not count as release

        object_supported(released_object) covers the gripper retracting away from the object
                without ever opening its fingers (e.g. contact breaks as the arm moves off) while
                the object is resting on a support -- still a deliberate release, just one that
                doesn't show up as a finger-opening motion
        also requires object_stable_relative(released_object), added 2026-09-02:
                object_supported alone fires on any contact with a support surface, including a
                one-frame bilateral-contact dropout mid-carry that happens to graze something
                while the object is still clearly moving -- confirmed false positive on
                ArrangeBreadBasket ep6 frame 445 (basket still moving 0.1-0.3 m/s) and ArrangeTea

                genuinely placed-down object should already be at rest relative to its support by
                the time the gripper retracts, so this doesn't narrow the intended case, only
                excludes the still-moving false positives. Uses object_stable_relative (not plain
                object_stable) for the same reason object_settled does -- relative to the
                support's own motion, so e.g. an object resting inside a basket that's still being
                carried doesn't read as "moving" just because the basket is.

                See CHANGES_2026-08-31.md item 16.
        uses object_supported (plain, not relative) as the base condition rather than
                object_stable: a freshly-dropped object is essentially never already resting on
                something at the exact frame contact breaks (it's still in free-fall), so this
                doesn't reopen the accidental-drop case the way a plain not-moving check could
                (which could read true for one frame before gravity builds up velocity) --
                object_stable_relative being ANDed in on top doesn't change this, since a
                free-falling object also isn't yet stable relative to anything either
        previously(gripper_is_opening) added 2026-09-02: gripper_is_opening is a raw single-frame
