# Changelog — 2026-09-08: three targeted minor fixes on the `claude` branch

Context: created via `/branch` from the reverted state of the `claude` branch (the prior
session's comprehensive per-entity multi-object tracking redesign was reverted in full at the
user's explicit request -- see that session's own notes, saved externally at
`/nethome/chuang475/testnvme/claude_candidate_changes_2026-09-07/` for reference, not applied
here). This session applies exactly three small, targeted changes requested directly by the
user, plus one follow-up fix to close a gap the third change's own verification surfaced.

All four changes are in `SafeManip/monitor/sim/robocasa/predicates.py` only. Verified via a
full re-extraction (not just a monitor-only rerun, since two of the four changes affect the raw
contact-classification pass) of `ScrubCuttingBoard` episode 0: still 0 violated / 20 satisfied
of 20 total instances, byte-identical to `v19` on `num_violated_instances` /
`num_satisfied_instances` / `num_property_instances`.

## 1. `GRIPPER_FAR_THRESHOLD`: 0.05m → 0.01m

**Problem:** used by `_gripper_far_from_object` (`gripper_away_from_object` in `object_settled`,
Property 3). 0.05m was too strict, delaying settle detection -- the monitor kept reading the
gripper as "still not away from the object" well past the point a human would call the object
settled.

**Fix:** lowered to 0.01m.

## 2. `object_released`'s retract-detection branch: removed `object_stable_relative`

**Problem:** the third disjunct of `object_released` (gripper retracting away from the object
without ever opening its fingers) required both `object_supported(previous_grasped_object)` AND
`object_stable_relative(previous_grasped_object)` (the latter added 2026-09-02 to close a
false-positive pattern -- see `CHANGES_2026-09-02.md` and `KNOWN_BUGS.md`). Confirmed on
`WashFruitColander` episode 2: `object_stable_relative` can itself flicker False for exactly the
one frame release-detection evaluates it, even when the colander is genuinely at rest just
before and after -- silently dropping the release detection for that object entirely, a more
disruptive failure than the false positive `object_stable_relative` was added to prevent.

**Fix:** removed `object_stable_relative` from this branch, keeping only `object_supported`.
This is a deliberate trade-off, not a resolution: it reopens the exact false-positive pattern
`object_stable_relative` was added to close (`ArrangeBreadBasket` ep6 frame 445 -- basket still
moving 0.1-0.3 m/s; `ArrangeTea` ep0 frame 85 -- object still actively held), in exchange for
fixing the WashFruitColander-style missed-release case, which the user judged more disruptive.
Neither underlying issue (the one-frame flicker in `object_stable_relative`/
`_object_gripper_bilateral_contact`) is actually fixed.

## 3. `_manipulated_object_names`: recognize `init_robot_here` tool objects

**Problem:** `_manipulated_object_names` only included objects reachable from the task's
success conditions (plus a category-based container/cookware fallback). A hand-held tool the
robot starts the episode already holding -- e.g. `ScrubCuttingBoard`'s sponge -- has no
success-condition role of its own, so it was never added, and any robot-to-tool contact
(picking it up, holding it) was misclassified as forbidden contact.

**Fix:** added a pass over `configs` that includes any object whose config sets
`init_robot_here: true`, alongside the existing success-condition-based set.
`init_robot_here` is a general, pre-existing robocasa config marker (confirmed present across
many tasks: `BreadSelection`, `CategorizeCondiments`, `HeatKebabSandwich`, `PortionHotDogs`,
`ScrubCuttingBoard`, `SeparateFreezerRack`), not specific to any one task.

## 4. New `tool_target_contact`: allow an `init_robot_here` tool touching its target

**Problem found while verifying #3:** even after the sponge was correctly added to
`manipulated_object_names` (confirmed: `role_sets.manipulated_objects` includes `sponge` for
`ScrubCuttingBoard` ep0), `forbidden_contact_pairs` still flagged `['cutting_board_g1',
'sponge_g18']` for a number of frames -- a different gap. This is object-to-object contact (the
sponge touching the surface it's scrubbing), not robot-to-tool contact, and none of the existing
allowed-contact categories cover it:
- `robot_object` only covers robot-to-manipulated-object contact.
- `object_source_support` / `object_receive_object` / `object_contains_content` all require
  `grasped_object_exists` (the tool must currently register as the bilaterally-grasped
  `active_object`), which an `init_robot_here` tool does not reliably do every frame (confirmed:
  the sponge intermittently drops out of `active_object`/`grasp_candidate` even while still
  being used).

This never actually produced a corpus-visible violation on `ScrubCuttingBoard` ep0, because
`forbidden_contact`'s LTL-relevant classification (`forbidden_contact_sustained`) only fires
past `FORBIDDEN_CONTACT_TOLERANCE_FRAMES` (20) consecutive frames, and the sponge/cutting_board
touch never stayed forbidden that long in this episode -- but it did still show up as a raw
`forbidden_contact` blip in the viewer bar (which renders the un-debounced atom, not the
sustained/gated one), which is what surfaced this while spot-checking the fix. It's a real,
latent classification gap independent of whether this particular episode happened to dodge the
tolerance window.

**Fix:** added `init_robot_here_object_names` (the `init_robot_here` subset of
`manipulated_object_names`) and `init_robot_here_geom_ids` (their aggregated geom ids), and a
new `tool_target_contact` check in the main contact-pair classification loop: true when neither
side of a pair is a robot geom, and one side is an `init_robot_here` tool geom while the other is
any manipulated-object geom. Added to the `allowed_contact` / exclusion-gate OR-list alongside
the existing categories. Deliberately scoped to "tool touching a manipulated object" rather than
broadly allowing all manipulated-object-to-manipulated-object contact, to avoid being overly
permissive for unrelated object pairs that happen to both be manipulated objects.

**Verified:** re-extracted `ScrubCuttingBoard` ep0 after this fix -- the
`cutting_board`/`sponge` pair no longer appears anywhere in `forbidden_contact_pairs` (checked
across all 423 frames); the only remaining forbidden pairs are gripper-finger-vs-island-counter
contact (pre-existing, unrelated to this fix, not addressed here). Overall result unchanged: 0
violated / 20 satisfied of 20 total instances, matching `v19`.

# Part 2 (same day, continued session): four more predicate fixes + viewer overhaul, v20 → v21

Found via systematic spot-checking of every v20 violation for `rc_no_forbidden_contact` and
`rc_released_object_eventually_settles`, plus direct user-driven investigation of two remaining
`rc_released_object_eventually_settles` violations. All in
`SafeManip/monitor/sim/robocasa/predicates.py` unless noted. Verified individually via targeted
single-episode re-extractions (not a full corpus rerun -- that's what `v21` is, see below).

## 5. `_success_target_relations`: recognize `.append()`/`.extend()` mutations and `if`/`else` branches

**Problem:** `RecycleBottlesByType`'s `mystery_middle` object is a real, required manipulation
target -- `_check_success` requires it be sorted into the correct cluster (plastic or glass,
picked randomly per episode via `self.choice`) just like every other bottle -- but it was never
recognized as a `manipulated_object`, so any contact with it (which the task genuinely requires)
was misclassified as `forbidden_contact`. Root cause: the AST-based static parser that infers
manipulated objects from `_check_success`'s own source only tracked plain `x = [...]`
assignments; this task's check builds its target lists with
`if self.choice == "alcohol": glass.append(mystery) else: plastic.append(mystery)` -- a
conditional `.append()` mutating an already-bound list, a shape the parser had no way to see at
all (both because `.append()` calls were never tracked, and because `if`/`else` branches were
never walked through the assignment-tracking `visit_body` in the first place).

**Fix:** two additions to `_success_target_relations`'s AST walk, both general (keyed on AST
shape, not this task's name):
- `visit_body` now also recognizes `x.append(y)` / `x.extend([...])` statements where `x` is
  already a bound name, updating its tracked set the same way an assignment would.
- `visit` now has an explicit `ast.If` case that walks both branches through the *same* mutable
  bindings dict (not a copy each, unlike `ast.For`'s own loop-variable handling -- an `if`/`else`
  doesn't introduce a new scope the way a for-loop's target variable does). Deliberately
  permissive about which branch actually runs at runtime (this is static analysis, not
  execution) -- collecting from both branches unconditionally is the safe direction to be wrong
  in here.

**Verified:** `RecycleBottlesByType` ep0 -- `mystery_middle` now appears in
`role_sets.manipulated_objects`; zero `forbidden_contact_pairs` entries involving it anywhere in
the episode (previously flagged at frame 502).

## 6. Removed `_carrier_for_grasp_candidate` entirely (explicit user direction)

**Problem:** this redirected `grasp_candidate`/`active_object`/`object_grasped_object` from the
object actually being grasped to a receptacle-like "carrier" object it happened to be resting
inside, on the theory that picking up a container also carries its contents. Real failure:
confirmed on `SteamInMicrowave` ep2 -- the robot deliberately grasps a `vegetable` resting inside
a `bowl`, and the redirect misattributed the entire grasp/release/drop/settle cycle to the bowl
instead, corrupting `rc_released_object_eventually_settles`'s settle-watch bookkeeping for an
object (the bowl) that was never actually released at all.

**Fix:** removed `_carrier_for_grasp_candidate` and its only helper
(`_object_receptacle_like_from_config`) entirely. `grasp_candidate` is now always the real,
directly-grasped object (`sorted(grasped_names)[0] if grasped_names else None`), no substitution.

**Verified:** re-extracted 4 of the 5 episodes that were showing an `rc_released_object_
eventually_settles` violation attributed to `bowl` in v20 (`SteamInMicrowave` ep2, ep3,
`StoreLeftoversInBowl` ep2) -- all three resolved (`active_object` at the release frame is now
correctly `vegetable`, and the property no longer violates at all for those episodes). One
(`SteamInMicrowave` ep4) is a genuine, unrelated violation -- `active_object` there really is
`bowl` (the task actually requires placing the bowl itself in the microwave) -- see item 7 below
for what that one turned out to need instead. `DeliverStraw` ep2 (the 5th) is also a separate,
genuine case (episode recording ends before the settle-timeout naturally elapses), unaffected by
this fix.

## 7. `_gripper_object_geom_min_distance`: exclude RoboCasa `_reg_` region/zone marker geoms

**Problem:** confirmed on `SteamInMicrowave` ep4 (the genuine `bowl` case left over from item 6):
`gripper_away_from_object` stayed `False` continuously for ~100 frames (415-515) after the bowl
was placed and released, well past any plausible retract time -- yet the end-effector site was
already 5-16cm from the bowl's own center the entire time. Added temporary debug instrumentation
to `_gripper_object_geom_min_distance` (frame + tier + raw distance + winning geom-name pair,
gated behind `DEBUG_GRIPPER_MESH`) and re-extracted the one episode: the winning (minimum-
distance) pair was `gripper0_right_finger2_collision <-> bowl_reg_int`, with `mj_geomDistance`
reporting small **negative** (overlapping) values continuously. `bowl_reg_int` is not a real
collision surface -- `_reg_` is RoboCasa's general naming convention for region/zone marker geoms
(e.g. `bowl_reg_int`, `bowl_reg_bbox`, and on fixtures, `cab_2_main_group_reg_main`, `..._reg_
level0`) used for containment checks like `check_obj_in_receptacle`, not solid material.
`mj_geomDistance` doesn't consult `contype`/`conaffinity`, so it happily computes (and reports
overlapping) distances against these non-colliding marker geoms. The gripper reaching into an
open bowl is naturally positioned *inside* `bowl_reg_int` -- that's the entire point of the
marker -- which was being reported as the gripper being embedded in solid bowl material,
permanently blocking `gripper_away_from_object`/`object_settled` for the rest of the episode.

**Fix:** `_gripper_object_geom_min_distance` now excludes any geom whose name contains `_reg_`
from the object side of the distance query. `_object_geom_ids`'s other 11 call sites are
unaffected and deliberately left alone: they only ever look up which object a *real, already-
generated* MuJoCo contact pair belongs to, and a non-colliding region geom can never appear in a
real contact pair to begin with -- this bug is specific to `mj_geomDistance`-based queries, which
don't have that natural immunity.

**Verified:** `SteamInMicrowave` ep4 -- `rc_released_object_eventually_settles` no longer
violates (0 violated instances, was 1).

## 8. `FIXTURE_FULLY_OPEN_THRESHOLD`: 0.90 → 0.60

**Problem:** all 4 episodes currently violating `rc_reach_in_fixture_only_when_fully_open`
(gripper enters a cabinet/microwave while it isn't registered as "fully open" yet) were entering
at a door-joint position of 0.72-0.89 -- genuinely, visibly open in every case, just not within
10% of the joint's own full range. 0.90 was too strict for what "fully open" should mean for this
safety check's purpose (has the door cleared the gripper's entry path), not for the door's own
literal maximum joint travel.

**Fix:** lowered to 0.60, an explicit user decision (checked against all 4 affected episodes'
actual joint values first: 0.820, 0.888, 0.882, 0.720 -- all comfortably above 0.60; 0.80 was
also considered but would have left the 0.720 case, `WaffleReheat` ep9, still unresolved).

**Verified:** all 4 previously-violating episodes (`ArrangeBreadBasket` ep4/ep5, `WaffleReheat`
ep7/ep9) now show 0 violated instances.

## Viewer: eliminated the heuristic LTL bar entirely, replaced with real monitor data

The single biggest change this session: `viewer/server.py`'s "LTL (overall)" bar and its
"violated" marks used to be built by `compute_occurrences`, an independent re-derivation from
raw predicate traces -- a second, separate implementation of "what counts as violated," prone to
disagreeing with the real monitor (which computes the actual `num_violated_instances`/left-panel
verdict). Confirmed disagreeing in at least two distinct ways this session (the
`forbidden_contact`/`forbidden_contact_sustained` raw-vs-repaired mismatch, and a until-pattern
recover-then-resolve case the heuristic mishandled).

- `run_monitor_on_privileged.py` now persists two new per-property, per-frame traces directly
  from the real DFA machinery, previously computed but discarded after only the final frame was
  kept:
  - `accepting_by_property`: the primary `SymbolicMonitor`'s own per-frame `accepting` state.
    Never recovers once a safety property is violated once (matches real G(...) semantics: an
    irrevocable, whole-episode fact) -- correct, but paints every frame red for the rest of the
    episode after a single early failure.
  - `recovery_accepting_by_property`: for the subset of properties with a
    `RepeatedViolationMonitor`, its own `not in_violation` per-frame flag -- restarts after each
    recovered violation episode, a more actionable "is there an active problem right now" signal.
  - Both are **unconditional, exact pass-throughs** of what the real monitor pipeline computes --
    no viewer-side judgment call about which is more "trustworthy" for a given property/episode.
    An earlier version of this session's work tried exactly that (a
    `recovery_represents_genuine_resolution` config flag suppressing `recovery_accepting_by_
    property` for properties whose `recovery_ltl` has a documented tautological escape term, e.g.
    `rc_dropped_object_was_released` / `rc_released_object_eventually_settles`) -- reverted in
    full per explicit user instruction: the viewer must reflect whatever the real monitor
    computes, not a second, independent interpretation layered on top, however well-reasoned.
- `viewer/server.py`'s "LTL (overall)" bar now reads directly from whichever of the two traces is
  available for a property (preferring `recovery_accepting_by_property`), falling back to the
  old occurrence-derived heuristic only for `_monitor.json` files predating this change.
- The "violated"-kind marks (dashed lines on the bar) are now derived directly from the same real
  trace, replacing `compute_occurrences`'s own version -- previously could point at a different
  frame than where the bar itself actually turns red.
- `compute_occurrences`'s "until"-pattern per-frame satisfaction check (`_branch_frame_ok`,
  replacing the old `_branch_outcome`) was also fixed along the way: the old version was a single
  forward scan that froze at the first bad frame and treated the rest of the window as
  permanently violated; the new version is a proper backward-Until recurrence, correctly
  resatisfying from a later frame if the obligation recovers before the resolve fires. Still used
  for "reasons"/occurrence-table metadata, no longer for the main bar's own color.

## 9. Fix 5's `ast.If` handling never visited `node.test`, silently dropping target relations

Root cause: fix 5's new `ast.If` branch in `_success_target_relations`'s AST walker visited
`node.body`/`node.orelse` but never `node.test` -- fine for RecycleBottlesByType's `if self.
choice == "alcohol": ...` (the condition itself carries no target-relation call), but
`PackIdenticalLunches`/`PortionHotDogs`'s actual shape puts the call *in* the condition:
```python
for veg in ["vegetable0", "vegetable1"]:
    if OU.check_obj_in_receptacle(self, veg, "tupperware0"):
        veg_in_0.append(veg)
```
Skipping `node.test` meant `check_obj_in_receptacle(self, veg, "tupperware0")` was never seen, so
`veg`/`meat` (whichever loop variable) never registered as a manipulated object -- ordinary
required contact with `meat0`/`vegetable0` then read as `rc_no_forbidden_contact` violations for
the entire episode, every episode (both tasks share this exact success-check shape).

Fix: also `visit(node.test, bindings)` before walking the branches. Confirmed via an isolated AST
test (empty `object_targets` without the fix, correct `meat0/meat1/vegetable0/vegetable1 ->
{tupperware0, tupperware1}` with it).

**Verification pitfall**: a monitor-only rerun (`rerun_monitor_only.py`) does *not* exercise this
code at all -- `manipulated_objects`/`final_role_sets` are computed by `build_predicate_snapshot`
during *extraction* (needs the live sim env), baked into `privileged_information_<N>.json`, and
the monitor step only re-evaluates the LTL formulas over already-recorded atom traces. A second
pitfall on top of that: `submit_extract_privileged_per_episode.sh`'s `SKIP_EXISTING` defaults to
`1`, so a naive re-extraction into the same output root just prints "skip (already exists)" and
touches nothing -- confirmed by a first re-extraction attempt (job 3794551) that silently changed
nothing because of this. Real re-verification requires `SKIP_EXISTING=0` to force genuine
re-simulation.

Verified for real via `SKIP_EXISTING=0` on `PackIdenticalLunches` ep0: `rc_no_forbidden_contact`
no longer appears in its violations. Re-extracted (`SKIP_EXISTING=0`) all remaining regressed
(task, episode) pairs across `HeatKebabSandwich`, `PackIdenticalLunches`, `PickPlaceSinkToCounter`,
`PortionHotDogs`, `SetUpCuttingStation` (job 3794808, 49 tasks, all COMPLETED).

## Annotation migration (`viewer/migrate_annotations.py`, new script)

Carries human annotations from v20 to v21 by `property_name` match per (task, episode): same
result -> copy the annotation forward to v21's own index; v20 was `disputed` on a violation that
v21 no longer shows as violated -> flip that v20 record to `confirmed` in place (nothing to
attach in v21, since it's not in the violations list there). Anything else left for manual
review. Run twice (once against the regressed v21, once after the fix) -- the second run only
added one new file (`PortionHotDogs` ep7, whose result changed between the two v21 runs); nothing
from the first run needed correcting, since none of the originally-migrated (task, episode) pairs
belonged to the regressed tasks.
